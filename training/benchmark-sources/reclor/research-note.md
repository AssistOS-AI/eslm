# ReClor source integration and direct development diagnosis

## Frozen delivery and rights boundary

This integration uses the official ReClor repository at Git revision `19b9d6c6025866ceafb4a4028819654b3817069b` and the official v1 release archive linked by that revision. The encrypted archive is 1,974,536 bytes and has SHA-256 `fc64ad8755e88d7ab353a4679101f6b9a7f22c7718ce57f993abd974920f055b`. The pinned README itself publishes the extraction password and names non-commercial research purpose as the delivery condition. It does not provide a separate dataset license identifier. ESLM therefore keeps the archive and extracted rows in the ignored local cache, uses them only for this non-commercial research program, and commits no source text.

The delivered edition contains 4,638 training records, 500 validation records, and 1,000 evaluator-only test records. Train and validation are streamed one object at a time from their native JSON-array files and validated against the exact five-field record shape. Every visible record has four non-empty answer candidates, a label in the source domain 0 through 3, and a unique split-local identifier. The adapter observed no duplicate visible task tuple in either opened split. The three native split files are the source shards; sequential processing retains every valid record without imposing a byte, row, or text-length quota.

The test file remains sealed. Its presence, byte length, and digest are verified, but the adapter does not parse its content, expose a test loader, join a test oracle, or execute it. This is intentionally narrower than source-schema validation because the task authority explicitly prohibits opening protected rows. A future test execution requires an accepted method, a frozen dependency set, and evaluator-authorized aggregate scoring.

## Label-free task projection

Each development record is projected into a generic `select-logical-reading-comprehension-option` task with a passage, a question, four candidates, and a `candidate-id` output contract. Candidate identifiers are hashes of candidate text plus a duplicate occurrence number, so permuting choices preserves the identity of the same semantic choice. The task identifier hashes the source family, split-local join key, passage, question, and visible candidates. It is used only to join a prediction to the private scorer; it is not an inference feature.

The numeric source label is never stored on the visible task. The host scorer converts it to one candidate identifier after the task has been built. Tests demonstrate that replacing the label leaves the visible task unchanged, that full nonce renaming preserves the task shape, that candidate permutation preserves the selected text when the label is permuted consistently, and that changing a premise changes the task. No ReClor string, identifier, label, answer position, or expected answer was added to the runtime core.

## What the complete validation execution establishes

All 500 official validation records were submitted to the unchanged direct symbolic engine. The Language Agent was disabled by construction and was invoked zero times. Every task returned `NO_APPLICABLE_METHOD` for the projected operation. Consequently, the system selected zero candidates and produced zero proof-bearing results. `benchmarkAccuracy` and `accuracyOnAnswered` are `null`: this is a complete 500-of-500 coverage execution with no attempted answers, not a 0% score.

The earliest executable failure is method selection. ReClor questions do not all denote one logical operation. The opened source includes, among other families, rule-constrained arrangement questions, necessary-conclusion questions, assumptions, strengthen and weaken questions, argument-role questions, flaw diagnosis, principle matching, and resolution of apparent discrepancies. A method that merely chooses among four strings would conceal these different proof obligations. The adapter therefore does not guess, apply a majority label, use option position, or install lexical overlap as reasoning.

## Why the core remains unchanged

A serious next cycle begins before choice selection. It must compile a passage into explicit claims, quantifiers, conditionals, exclusions, ordering constraints, causal claims, evidence relations, and argument roles; classify the question into a typed operation; compile each candidate as a proposed conclusion, premise, attack, repair, model, or constraint assignment; then select a registered method whose witness matches that operation. Necessary-conclusion tasks require a proof or exhaustive countermodel search. Constraint games require a satisfying assignment and, when the question says “must,” a refutation of every counterexample. Strengthen and weaken tasks require an explicit support or attack graph. Flaw and principle questions require a typed argument schema and a structural comparison witness.

Those representations do not yet exist for the unrestricted source prose, and a development trace stopped before it could support reliable subcluster counts. A generic-core proposal is therefore deferred rather than invented. Before any future proposal can pass Core Guardian, it must survive complete entity, predicate, relation, and surface renaming; option permutation; irrelevant distractors; conditional reversal; quantifier and polarity contrasts; missing-premise controls; deterministic replay; resource bounds; witness verification; and unrelated benchmark regressions. Only after those development-visible gates pass may a frozen, aggregate-only test evaluation be authorized.

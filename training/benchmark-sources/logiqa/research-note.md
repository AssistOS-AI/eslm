# LogiQA source integration and direct English development diagnosis

## Frozen bilingual source and rights boundary

This integration freezes the official LogiQA data repository at Git revision `ff6c4cbca47627b3ac2da94a29fa28204a167b41`. The release contains 7,376 training, 651 evaluation, and 651 test cases in English and the corresponding 7,376, 651, and 651 cases in Chinese. The adapter retains all six files as native source shards, for 17,356 language-version records representing 8,678 semantic cases per language. Every opened file is read sequentially, one eight-line record at a time; no row is removed because of file size, duplicate text, presentation anomaly, current language coverage, or absent reasoning capability.

The official repository publishes the data and requested paper citation, but it contains no `LICENSE` file and its pinned README states no dataset license. A third-party mirror's license field is not authority for the official release. ESLM therefore applies a narrow local academic-research and no-redistribution policy while rights remain unclear. Original text stays in the ignored cache. The committed receipts contain only source identities, aggregate schema counts, anomaly counts, and ESLM-authored analysis.

English and Chinese training and evaluation files are validated against the source owner's eight-line contract: a blank separator, a lower-case correct-choice letter, one passage line, one question line, and four physical option lines. The source contains 13 duplicate visible English training tasks and 52 duplicate visible Chinese training tasks; they are retained. Decorative option prefixes are inconsistent. Across opened files, 775 English training option lines, 20 English evaluation option lines, 1,220 Chinese training option lines, and 6 Chinese evaluation option lines use a prefix that is missing, reordered, lower-case, full-width, space/comma-delimited, or otherwise differs from canonical `A.` through `D.` presentation. The README defines the remaining four physical lines as the four options, so the adapter uses physical slot order for label semantics and treats prefixes only as counted surface data. It never changes a label because a decorative prefix is malformed.

Both English and Chinese test files remain sealed. Their presence, byte length, and digest are verified without parsing their content. No test loader, test oracle join, per-item result, or test execution is exported. The English evaluation split is the only executed development scope. Chinese evaluation is fully retained and schema-validated but reported as outside the current English language profile, not as 651 failures.

## Label-free task and oracle boundary

The adapter projects an English evaluation record into the generic operation `select-logical-reading-comprehension-option`. The visible task contains the passage, question, four physical candidate texts, and a `candidate-id` output contract. A candidate identifier depends on its normalized text and duplicate occurrence, not its position or correctness. The task identifier incorporates a non-semantic join key and the complete visible tuple. Neither identifier is inspected by a reasoning method.

The answer letter remains inside the host scorer. It is converted to the corresponding physical candidate identifier only after the visible task is built. Changing `a` to `c` leaves the task byte-for-byte unchanged. Tests replace every domain word with nonce vocabulary, permute candidates and update the label consistently, reverse a premise, and introduce decorative prefix disagreement. These controls show that adapter behavior follows declared record structure rather than source IDs, strings, hashes, majority labels, or expected answer positions.

## Complete English development execution

All 651 English evaluation cases were executed through the unchanged direct symbolic engine. No Language Agent was available or invoked. Every case returned `NO_APPLICABLE_METHOD`, so no option was selected and no witness was produced. The receipt records `tested: 651`, `available: 651`, and `answered: 0`. Both benchmark accuracy and accuracy over answered cases are `null`. This avoids the false statement that the system scored 0%: the execution established complete method-coverage failure, not 651 incorrect symbolic conclusions.

The source's label distribution is not used as a baseline or fallback. The evaluation labels are uneven, but predicting a majority letter would be an answer-position policy with no reasoning witness. Likewise, lexical overlap between a passage and an option cannot establish necessity, weakening, contradiction, structural analogy, or satisfaction of a combinatorial constraint.

## Why no core method was added

LogiQA combines several distinct operations. Some questions ask for a categorical consequence; some require conditionals and contraposition; some describe ordering, assignment, grouping, or selection constraints; some ask which premise strengthens or weakens an argument; some ask for a flaw, principle, explanation, or structurally similar argument. Each requires a different intermediate representation and a different witness. A single `select option` engine branch would erase these distinctions and provide no reviewable evidence that the selected text follows.

A future cycle must first compile passage claims, quantifiers, conditionals, exclusions, order and cardinality constraints, causal claims, support and attack relations, argument roles, and each candidate's semantic contribution. It must classify the question without consulting the answer. Deduction requires a proof; “must” constraint questions require absence of a counterexample; possibility questions require a satisfying assignment; weaken and strengthen questions require an explicit attack or support delta; analogy questions require a typed correspondence witness. Chinese evaluation additionally requires a separately specified direct-language compiler, not silent translation into the English score.

No such compiler or common trace-supported failure cluster exists at the current checkpoint, so no generic-core proposal was made and Core Guardian was not asked to approve an empty solver shell. Before a future proposal is admissible, it must pass full entity, predicate, relation, and surface renaming; candidate permutation; irrelevant distractors; conditional reversal; quantifier, polarity, and cardinality contrasts; malformed decorative prefixes; proof verification; bounded-resource replay; and all unrelated regressions. The protected test files remain closed until an accepted method and its executable dependencies are frozen.

# Benchmark-Guided Symbolic Learner

## Purpose and evidence boundary

Use benchmark failures as experimental observations, not answer-writing instructions. Validate `ASSIGNMENT.json` and read only authorized working, regression, fresh, and aggregate shadow evidence. Hidden or shadow cases do not become agent-visible because a local path exists. Preserve the current accepted checkpoint and never stack a new hypothesis on an unaccepted candidate.

## Establish the baseline

Before editing, map available information, answer contract, recurring relations and concepts, linguistic constructions, ambiguity and uncertainty, required reasoning depth, world or domain scope, external knowledge dependency, and expected proof. Sample every meaningful metadata stratum rather than only early or easy cases.

Run the host ESLM through an external CLI tool when authorized. Capture semantic parses, task frames, selected KBs and shards, selected methods, proof or execution traces, unresolved subgoals, final statuses, latency, memory, KB bytes, and core bytes. A correct answer reached through an invalid trace remains a failure.

## Cluster and classify

Cluster at the earliest incorrect stage. Language clusters include normalization, lexicon, construction, role, reference, negation, quantifier, and ambiguity. Knowledge clusters include missing term, fact, ontology, event frame, time, space, world, domain, perspective, and modality. Reasoning clusters include rule, composition, transition, default, exception, contradiction, confidence, and search. Planning clusters include KB selection, shard routing, posting, pruning, budget, and method selection. Output clusters include ranking, epistemic status, realization, proof rendering, and abstention. Runtime clusters include malformed input, checksum, memory, timeout, and nondeterminism.

Choose KB or core before implementation. Facts, lexical mappings, source ontologies, event frames, domain defaults, relation semantics, and ontology-specific composition are KB data. A core candidate requires several independent examples with one structural cause, usefulness after all domain vocabulary is renamed, evidence that a KB workaround would duplicate or distort meaning, and abstract tests. One failed question never authorizes a core patch.

## Candidate and challenge circuit

Implement the smallest reusable candidate. Do not encode exact sentences, record IDs, question hashes, benchmark names, answer indices, or entity exceptions justified only by occurrence. Preserve entailed, default, likely, possible, unknown, contradicted, ambiguous, and unsupported distinctions.

Run focused cluster tests, nearby structural variants, meaning-preserving metamorphic tests, meaning-changing contrastive tests, the current regression pool, affected historical suites, core unit tests, fresh unseen samples, and aggregate-only shadow evaluation. Vary names, nonce words, locations, voice, clause order, pronouns, distractors, temporal expressions, relation direction, negation, premise presence, exceptions, depth, and ambiguity.

Accept only when the target cluster improves on fresh evidence, proofs and abstention remain valid, execution failures do not increase, no material capability regresses, and KB/core/resource growth is explained. Reject and return to the accepted checkpoint when a fix works only on inspected wording or gains certainty without evidence.

## Research record

Every cycle contains `cycle.json`, pool manifest, baseline reports, candidate reports, failures, comparison, and `research-note.md`. The note records the cluster, trace-supported root cause, KB/core decision, change, target delta, fresh and metamorphic results, regressions, proof audit, resource growth, counterexamples, and accepted checkpoint or rejection reason.

A benchmark is substantially integrated only after repeated unseen samples stabilize, structural generalization and proof validity remain high, previous competencies survive, shadow aggregates confirm the gain, and remaining failures form recognizable hard classes.

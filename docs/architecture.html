ESLM Documentation / Architecture and runtime

Trusted runtime, declarative knowledge, explicit planning, and evidence-bearing results

The architecture is built around authority boundaries. Trusted source code defines schemas, parsers, planners, inference operators, caches, and validators. Knowledge packages contribute only validated data. Training agents propose candidates outside the deployed runtime. Every transition between these regions has an explicit format and validation gate.

Repository and execution layers

The command layer parses operator intent and creates a configured runtime. The language layer converts utterances into symbolic queries and session assertions. The KB layer validates canonical records, compiles deterministic shards, opens manifests, routes queries, and projects declarative records into the indexes consumed by reasoning. The reasoning layer registers capabilities, constructs plans, performs bounded inference or state execution, and emits proof or gap evidence. The training layer prepares isolated workspaces and may invoke a Coding Agent only through an explicit training command. That training authority is separate from the operator-side Language Agent, whose only authority is bounded translation or simplification after a direct UNPARSED result.

An operator-normalization layer now exists beside, not inside, the deployed runtime. The general CLI creates this wrapper by default, while --no-external-language-agent removes it and EslmRuntime never imports it. The wrapper observes a complete direct result, invokes an external Language Agent process only for UNPARSED, validates the returned language object, and submits accepted English to the same runtime again. It cannot call reasoning operators directly or inject knowledge. Because this wrapper owns process and cache access, it is an operator tool even though its entry point is the same CLI.

These layers are not interchangeable. The CLI may select a KB, but it cannot bypass package validation. A KB may contain rules, but it cannot introduce an inference operator. A training skill may propose a generic-core change, but it cannot promote or execute that change. A reasoning method may request indexed data, but it must obey the configured cache and shard budget.

Generic core versus knowledge packages

The generic core contains domain-independent operations: token normalization, construction matching, variable binding, task construction, capability selection, safe Horn unification, proof assembly, provenance traversal, context checks, trust policies, result realization, and bounded storage. It can know what an assertion is and how a rule is executed. It must not know that penguins swim, what “dog” means in a particular lexical resource, or which commonsense consequences accompany apologizing.

A KB package contains terms, lexical forms, assertions, rules, contexts, provenance, mappings, and source-oriented indexes. Its manifest identifies the package, schema, version, compiler, source hash, record counts, shards, and shard hashes. Because package content is declarative, loading it does not grant it filesystem, process, import, or network authority. Provider-specific compact formats such as the current Open English WordNet and ATOMIC packages remain data and are accessed by trusted adapters.

Task planning and method selection

A capability descriptor states the goal kinds it can address, required input forms, preconditions, cost information, output form, and verification obligations. The planner matches a task frame to these descriptors and produces steps such as observing relevant shards, deriving a result, verifying the derivation graph, and constructing the requested output. A plan is therefore reviewable before and after execution.

The Stage A planner prefers indexed retrieval for direct facts and safe Horn deduction for compositional queries. It now also selects method:core:temporal-state-predecessor for one location-before form and method:core:configured-induction when a loaded package licenses the queried predicate. Both require explicit input structures and preserve their witnesses or observations. An unsupported goal produces a structured gap. The planner must not quietly fall back to a plausible string completion.

The Entity Tracking adapter uses the complementary structured-task entry point. It emits complete-container-contents with no label and compiles the source's box and verb syntax into finite-relation-state-program-v1. The runtime selects method:core:container-state-transitions, which sees only typed contains assertions, transfer, add, and remove operators, and a relation query. It bounds subjects, transitions, and values and returns the final semantic values plus a trace. This method is generic because the adapter-owned source words, subject identifiers, relation values, and item names can all be replaced without changing the algorithm. The official span remains in a host-only oracle used after execution.

Typed relation composition

The relation-algebra entry point accepts a graph of typed edges, entity features, two query endpoints, and one declarative algebra. It validates every identifier and relation reference, adds only inverse edges declared by that algebra, and explores paths under explicit depth and state budgets. A dynamic composition table reduces the edge-class sequence. The result is refined into an output relation only when the target endpoint's features support that refinement. The trace retains every asserted or inverse edge and the nested composition witness.

CLUTRR uses this route through structured source fields rather than pretending that its generated narrative is already supported controlled English. The adapter owns graph extraction and source schema validation. clutrr-kinship-algebra owns the licensed relation inventory, gender-sensitive refinements, inverse table, and composition table. Trusted code owns traversal, composition, ambiguity, inconsistency, and budgets. If two source cases present isomorphic typed evidence but request distinct blood and in-law labels, the runtime returns ambiguity; adding an item ID branch would violate the method's input semantics.

World compatibility and context preference

Semantic compatibility converts bounded text into ontology-declared unary, binary, proposition, comparison, change, possessive, material, action, and numeric frames. It normalizes argument order and polarity, derives only declared inverse relations and implications, compares target frames with context frames, and emits signed evidence. world-relations-1.0 owns the reviewed English constructions and their semantic mappings. ConceptNet may add independently sourced relation evidence through the same provider-neutral interface. Neither source is allowed to contain an EWoK row or preference label.

The EWoK adapter uses that general operation twice: it holds one target fixed, scores it with each visible context, and requires the designated context to receive a strictly higher score. A tie is a failed preference, not an invitation to choose a candidate position. This local scalar protocol is intentionally described as a symbolic diagnostic rather than the benchmark's official language-model probability protocol.

Narrative continuation selection

The narrative compiler represents each context sentence and candidate ending as a bounded event frame: content terms, predicate candidates, named participants, pronoun groups, polarity, modality, and tense. The continuation method calculates declared structural features such as participant continuity, content bridges, tense agreement, polarity conflict, and lexical novelty. Selected providers can add bounded causal, goal, event, social, state, or contradiction evidence. Every feature records its value, weight, contribution, and provenance.

The selector returns a defeasible candidate only when its score exceeds the declared minimum margin; otherwise it abstains. Story Cloze's development-visible feature policy lives in the adapter with calibration provenance. Candidate identifiers come from visible content rather than answer positions, and the host-only correct ending never enters the task. This makes the computation reviewable without inflating a bounded continuation ranker into a claim of unrestricted narrative understanding.

Factoid routing

A recognized factoid question becomes a provider-neutral frame containing WH type, construction, relation surface, direction, subject when recoverable, and conservative provider paraphrases. Every loaded provider is consulted independently. Equal semantic answer sets are merged with all provenance; distinct answers or provider-declared ambiguity produce AMBIGUOUS. Provider order never decides the answer. When no provider responds, the runtime returns a structured factoid knowledge gap rather than mislabeling the recognized question as unsupported language.

This route lets GeoNames, ConceptNet, Open English WordNet, and other independent packages contribute to SimpleQA-like questions without importing a SimpleQA reference answer. It improves the boundary between parsing and knowledge coverage; it does not claim encyclopedic completeness or replace the benchmark's semantic grader.

Reasoning and proof evidence

Retrieval returns the record identity and provenance that directly support a value. Deduction recursively satisfies rule premises, maintains substitutions, prevents unsafe variable escape, and records rule depth. A derived value cites the rule and the supporting facts or subproofs. Negative conclusions require explicit negative evidence or a declared closed-world policy; absence alone is not ordinary proof of falsehood.

Inductive conclusions are hypotheses supported by observations and must be labeled as learned, scoped, and defeasible. The current bAbI policy is declarative KB data: it names the color value domain, the implicit query trigger, support and coverage thresholds, and latest-member selection. The core owns only the reusable induction mechanism and refuses to invent a policy for an undeclared property. Abductive conclusions are explanatory candidates and must not be represented as established facts. This distinction survives realization so a human answer cannot conceal the epistemic status of its underlying result.

Temporal predecessor evidence contains the previous and boundary events from ordered session history. Container-state evidence is an execution trace rather than a Horn proof. Each result names the method it used, which lets reviewers distinguish retrieval, deduction, induction, state-history lookup, task-program execution, and abstention even when two methods happen to produce the same surface answer.

Memory, routing, and caches

Small packages may be loaded eagerly. Large packages use manifest metadata and query-derived routing keys to select only relevant shards. The cache has an explicit memory policy, reserve, byte target, and eviction behavior. Cache occupancy and loaded-provider information are exposed in runtime metadata. A soft memory target is not advertised as a hard operating-system guarantee.

Routing is part of correctness. If a key cannot map conservatively to all potentially relevant shards, the loader must broaden the selection or report the limitation; it must not omit evidence merely to remain fast. Paths from manifests are resolved against an allowlisted package root, and hashes are checked before records are trusted. No package field becomes an import specifier.

The result protocol

eslm-runtime-result-v1 reports the original and normalized input, parsed query, task frame, selected plan, status, answer, semantic values, provenance, reasoning method and depth, session context, language route, used KB versions, unresolved subgoals, and memory policy. SOLVED means the requested contract was met. UNPARSED means the language or task could not be compiled. Other detailed internal statuses and gaps distinguish missing knowledge, capability, trust, or resources.

An assisted result adds the original direct failure and a normalization object containing trigger, exact model, cache attribution, digests, bounded process receipt, candidate, validation, and reparse status. language-agent-normalized, language-agent-normalization-failed, and language-agent-normalization-rejected are visible route distinctions. A textual answer is only one view of this object. Evaluation scores semantic fields and diagnostics, not terminal decoration. Batch mode writes one structured result per input. Interactive mode maintains session context but uses the same engine and result protocol.

Security and determinism

The runtime has no dependency on Language Agent, an LLM service, or network data. It does not execute strings from documents, benchmarks, manifests, or shards. Canonical validation rejects unknown record types, invalid identifiers, dangling references, unsafe rules, missing provenance, and malformed contexts. Compilation sorts records and writes stable JSON so equal inputs and compiler versions produce equal content hashes.

The optional normalizer is intentionally outside this deterministic claim. It runs in a new empty temporary directory with a read-only sandbox, no approval escalation, ignored user configuration and repository rules, disabled tools, a bounded environment, and a strict response schema. Its output is untrusted and never executed. Cache keys bind model and policy versions, and cache hits remain assisted evidence. Local successful receipts establish an operational Language Agent CLI observation only; the project does not infer API support from them.

Determinism includes failure behavior in the direct profile: the same package set, task, runtime version, budgets, and session state must produce the same plan choice and semantic result. Timestamps belong in build or external-process receipts where they describe an event; they do not participate in canonical shard identity.

Reviewer trace

For a runtime change, begin at the task contract, identify the owning layer, follow all data crossing into that layer, and verify both successful and failing paths. For a package change, compare source and packet hashes, canonical record validation, compiled manifest and shard hashes, query routing, proof provenance, negative controls, and regression results. For a new method, inspect its descriptor, applicability checks, bounded execution, proof obligations, failure form, and domain-independence. For normalizer changes, additionally verify direct-first triggering, exact model arguments, tool and workspace isolation, anchor preservation, the bounded three-proposal feedback protocol, reparse, cache invalidation, and route metrics. The exact contracts are maintained in DS002, DS006, DS008, and DS013.

ESLM Documentation / Architecture

Runtime and model architecture

The architecture separates transferable algorithms in src/ from corpus-conditioned executable data. The promoted bAbI-derived core lives in training/model/; independently loadable QUICK, WordNet, and ATOMIC modules live below training/KBs/. This boundary lets a coding agent change learned knowledge while preserving the reviewed language and inference engine.

Language compilation

Purpose. This diagram isolates the part that interprets language. The normalizer produces tokens and correction records. The parser matches supported English constructions and resolves their slots. The query contract is a structured object consumed by the reasoner; it contains no executable source from the user.

The relevant modules are language.mjs, parser.mjs, and the orchestration in engine.mjs. A failure here is reported as unsupported or ambiguous before knowledge execution starts.

Knowledge execution

Purpose. This diagram shows the reasoning boundary. Subject, predicate, and object postings narrow candidate facts. The rule engine derives additional facts by unification. The output preserves direct sources, rule ID, and supporting fact IDs.

reasoner.mjs builds indexes over direct and derived facts. Duplicate signatures and the maximum round count bound closure. The engine never treats a missing proof as false.

At engine construction, deriveClosure(model) starts with direct facts and applies each rule for at most eight rounds. indexFacts(facts) then builds maps by subject, predicate, and object/value. With --kb space-geography, “Where is Neptune?” intersects the neptune subject posting with the located_in predicate posting and returns the direct Solar System fact. With --kb child-basic, the Jhon mortality query instead reaches a fact derived through three rules.

Response construction

Purpose. This diagram shows that wording follows verification. realizer.mjs selects an English sentence form and model display names. engine.mjs returns that sentence together with status, semantic values, normalization details, query, provenance, conversation context, and explicit active-model/KB comparability metadata.

Stable core and generated model

Purpose. This diagram defines ownership and configuration. Stable algorithms implement normalization, parsing, indexing, rules, tracing, and realization. The promoted generated model provides corpus-conditioned constructions. Optional KB modules add persistent entities, facts, and rules. The manifest remains the entry point for each artifact, while mergeModels constructs and validates the selected active view.

Generated moduleRuntime use

QUICK and its three components use the seven-module graph contract shown in the table. When those graph modules are selected, matching entities are combined, semantically identical facts and rules are deduplicated, and indexes are rebuilt from the merged fact positions. WordNet and ATOMIC deliberately do not force their data through that graph: WordNet uses lemma-to-many-synset postings plus hypernym adjacency, while ATOMIC uses normalized-event postings grouped by relation. runtime.mjs asks the declared public providers first, then delegates other supported constructions to the v1 graph engine. Every response lists the selected KB IDs and disables direct comparability with the clean benchmark configuration.

Candidate trust boundary

Purpose. Generated JavaScript is treated as untrusted until validation. The static scan rejects ambient capabilities such as networking, child processes, dynamic code compilation, and corpus-selected imports. Semantic validation checks the format, entity references, fact shape, provenance, rules, and generated indexes. Human review remains required before promotion.

validateGeneratedModel reads every candidate .mjs source and applies the forbidden-pattern policy. It then imports only manifest.mjs and calls validateModel. The validator recomputes subject, predicate, and object postings from facts.mjs and compares them with indexes.mjs. A stale position fails validation.

Scaling boundary

The v1 fact/rule engine builds complete bounded closure and posting lists in memory, requires aliases to resolve uniquely, validates whole indexes, and rebuilds closure for session overlays. The source-specific providers avoid the alias restriction—WordNet can map one lemma to many senses—but their manifests still import all shards. These are explicit blockers, not optimizations hidden behind a scale claim.

The Scale and Context review now has real measurements from complete WordNet and ATOMIC builds. Source-specific providers preserve polysemy and defeasible event relations, but their static manifests still assemble all shards eagerly. ConceptNet and GeoNames cannot proceed until query-directed import, interned dictionaries, scope-aware shards, and bounded reasoning replace this whole-profile allocation.

ESLM Documentation / System / Grounded failure

Useful related knowledge without pretending that it answers the question

When ESLM cannot establish an answer, it can still search the selected knowledge sources for bounded, provenance-bearing records related to the request. The primary failure remains unchanged. The additional grounding bundle is retrieval material for a person or a separately evaluated downstream model, not a proof and not a hidden second answer.

Two outputs with different authority

An answer exists only when a registered symbolic method satisfies the requested output contract. Related evidence needs a weaker condition: an entry may match an accepted entity or predicate, or it may have bounded lexical overlap with the visible request. That weaker match is useful for recovery but cannot justify a truth claim.

This separation is the central invariant. A user interface may display both objects together, but labels and data structures must make their different authority unmistakable.

When automatic grounding runs

The current EslmRuntime.ask path considers grounding only after one of these primary statuses:

  • UNPARSED, when safe Semantic IR could not be built;
  • UNKNOWN or MISSING_KNOWLEDGE, when the answer lacks sufficient premises;
  • NO_APPLICABLE_METHOD, when the required transformation is unavailable;
  • PARTIAL or UNSUPPORTED_OUTPUT, when execution did not satisfy the complete output contract;
  • AMBIGUOUS, UNDERDETERMINED, or INCONSISTENT_CONTEXT, when several interpretations, solutions, or conflicting premises remain.

SOLVED and DEFEASIBLE results do not launch failure grounding. Neither do specialized outcomes that are not in the trigger set. A permitted status also does not guarantee a bundle: if no selected source exposes a grounding receipt, the runtime returns the primary result alone.

The current implementation never launches grounding after RESOURCE_LIMIT. Primary execution has already exhausted declared authority, and an automatic second search could worsen overload or hide the real failure. The target contract permits a later product to reserve a separate grounding budget before execution, but the present runtime does not implement that reserved post-limit route.

Automatic grounding is currently attached to text requests through EslmRuntime.ask. A direct typed call through executeTask does not automatically enter this fallback. This is an implementation boundary, not a claim that typed failures never need related evidence.

How the bounded search works

  1. The runtime creates one eslm-grounding-request-v1 from the visible request and the accepted query fields, when any exist.
  2. It selects a bounded set of informative surface terms, removes a fixed set of request words, and adds conservative singular variants. An unsuccessful spelling correction does not become accepted semantics.
  3. The loaded canonical model uses prebuilt subject, predicate, object, value, and alias postings. The session builds a bounded temporary direct-fact projection for this failure; it does not rebuild the immutable base closure or index. Selected public providers use their reviewed exact indexes. A provider without the required interface returns an incomplete receipt instead of being treated as an empty authoritative source.
  4. Entries are validated, deduplicated, and ranked by explicit semantic identity and visible overlap reasons. Stable tie-breaking and cross-KB round-robin selection keep provider order from deciding the returned set.
  5. The runtime returns at most the bundle limit, currently eight entries in the ordinary path, plus a receipt for each scheduled search surface. A reserved aggregate receipt accounts for sources omitted by global source, lookup, candidate, byte, or receipt budgets, so omission can never look like a complete empty search.

The fallback does not scan every fact, closure record, source event, or shard. Posting expansion, term selection, lookups, values per lookup, entry payload, provenance, structural depth, and final output are bounded independently. A short result list is therefore not evidence that the whole knowledge collection was searched.

Reading the bundle and its receipts

The bundle protocol is eslm-grounding-bundle-v1. Its top-level triggerStatus records the primary failure, queryText records the bounded visible request, and interpretation repeats the non-proof warning. Each entry contains a KB identity, record identity, short statement, typed semantic value, epistemic status, provenance, contributing KB versions, relevance score and reasons, and a witness when the entry was derived.

Each receipt reports one search surface: KB and version, access-path coverage, provider status, candidates considered, whether that search completed, and any truncation or provider failure. Consumers must evaluate receipts, term selection, and output limits separately.

Bundle fieldExact interpretation
status: RELATED_EVIDENCE_FOUNDAt least one entry was returned. The search may still be incomplete; inspect search.complete.
status: NO_RELATED_EVIDENCENo entry was returned and every receipt plus term selection completed. This is bounded absence under the declared search, not a universal proof that no relevant knowledge exists.
status: SEARCH_INCOMPLETENo entry was returned, but term selection, a provider, or a bounded posting search did not complete. Absence is inconclusive.
search.completeAt least one receipt exists, every receipt is complete, and term selection completed.
limits.outputTruncatedMore validated, ranked entries existed than the output limit allowed. This can be true even when the underlying bounded searches completed.

A bundle that contains entries and has an incomplete receipt still uses RELATED_EVIDENCE_FOUND; its search.complete value remains false. Evidence presence and search completeness answer different questions.

A concrete result

With the tutorial quick KB loaded, Can Penguin fly? is understood but unsupported. The primary result remains UNKNOWN with no values, no answer provenance, and no used KB version. Related facts about the same entity can still be useful. This abridged JSON view omits unrelated result fields and some receipt and entry detail:

{
  "status": "UNKNOWN",
  "answer": "I understand the question, but I do not have evidence for a yes or no answer.",
  "values": [],
  "provenance": [],
  "usedKbVersions": [],
  "grounding": {
    "format": "eslm-grounding-bundle-v1",
    "status": "RELATED_EVIDENCE_FOUND",
    "triggerStatus": "UNKNOWN",
    "answerSupported": false,
    "search": {
      "complete": true,
      "termSelectionComplete": true,
      "receipts": [{
        "kbId": "quick",
        "kbVersion": "1.0.0",
        "status": "matches-found",
        "complete": true,
        "truncationReasons": []
      }]
    },
    "entries": [{
      "kbId": "quick",
      "kbVersion": "1.0.0",
      "recordId": "fact:quick:penguin-swim",
      "statement": "Penguin can swim.",
      "epistemicStatus": "asserted",
      "provenance": ["prov:quick:authored-v1"]
    }]
  }
}

The entry supports the statement that Penguin can swim. It does not support either “Penguin can fly” or “Penguin cannot fly.” A consumer that turns this record into a flying answer has crossed the authority boundary.

The same principle applies after a parse failure. For example, a session may accept Zara is a pilot. and then fail to parse Write a report about Zara.. Grounding can return the session fact to help a person reformulate the request, while the primary status remains UNPARSED.

Using the bundle with a downstream language model

ESLM does not currently include a downstream answer-writing model. An external product may provide the visible question and structured bundle to a model, but that creates a separate assisted-generation route. It must preserve the primary status and answerSupported: false, require citations to returned record identifiers, disclose incomplete search, and measure unsupported claims independently.

The downstream model must not be confused with the operator Language Agent normalizer. The normalizer receives only the language request and bounded parser feedback after direct UNPARSED; it never receives grounding entries, KB search results, answer values, or proof state. This prevents a translation helper from becoming an undeclared question-answering model.

A safe downstream consumer follows this order:

  1. Read the primary status, answer, values, and provenance first.
  2. Treat every grounding entry as a possibly useful source claim, not as a conclusion.
  3. Check search.complete, every receipt, and outputTruncated before making an absence claim.
  4. Cite the KB version, record ID, and provenance for every statement derived from an entry.
  5. Label generated prose as downstream formulation and never replace the original ESLM result in logs or evaluation.

Current boundary and verification

The implemented foundation searches exact postings in the loaded canonical model and session overlay plus bounded provider-specific grounding indexes. It does not yet provide general book-scale span retrieval, automatic interpretation of every canonical record kind, semantic embeddings, unrestricted cross-KB proof-frontier expansion, or a downstream prose generator. Lexical overlap can retrieve distractors and can miss a semantically related record whose vocabulary differs; that is why entries remain non-authoritative and receipts expose the searched scope.

Focused tests verify an unknown result with separate related evidence, no grounding after a solved answer, correct contributor-only KB accounting, original-surface retrieval after UNPARSED, session evidence, conservative plural handling, provider-order invariance, cross-KB diversity, entry bounds, complete versus incomplete empty searches, interactive labeling, separate trace receipts, and the prohibition on automatic retrieval after RESOURCE_LIMIT.

The normative owners are DS009 for answer and grounding authority, DS020 for bounded retrieval and receipts, DS021 for resource budgets, DS007 for CLI presentation, and DS010 for the independent product and downstream-model benchmark.

ESLM Documentation / Evaluation and gates

Capability evidence, split isolation, negative controls, regressions, and falsifiable claims

Evaluation asks what capability a result supports and under which evidence regime. It does not treat one aggregate benchmark score as a description of the whole system. Each report binds a suite, split policy, runtime version, KB versions, memory policy, semantic scorer, diagnostics, and resource measurements.

Levels of evidence

Unit tests establish local contracts such as record validation, rule safety, deterministic IDs, and path rejection. Integration tests establish that the frontend, planner, KB loader, inference engine, and result protocol work together. Capability suites vary language form and logical structure while holding the intended operation stable. Source-KB tests sample real package indexes and compare eager and lazy behavior. Benchmarks measure externally recognizable tasks but remain interpreted through the capability taxonomy.

A claim must name its level. Passing an authored smoke KB is implementation evidence, not broad world-knowledge evidence. Answering sampled WordNet definitions is source-adapter evidence, not general question answering. Solving a bAbI task can support a narrow relation or deduction claim only when controls show that the system did not memorize entity names, position, or answer frequency.

The current catalog has seven reviewed benchmark families: BLiMP, bAbI, CLUTRR, Entity Tracking, EWOK, Story Cloze, and SimpleQA. Catalog review confirms task relevance, a primary source, and a recorded license or access gate. It is not execution evidence. After the reset, only the five-case native fixture has a published run; its 5/5 result verifies the local scorer and runtime paths and is marked non-comparable. Public-dataset rows remain pending until acquisition, adapter, split, and checksum requirements are satisfied.

Split isolation

Training-visible records may be read by a synthesis subprocess. Development-visible cases may be clustered for diagnosis and iterative proposals. Test and hidden cases are evaluated only by trusted local tools after candidate construction. Packet manifests and execution receipts make this boundary auditable. If leakage occurs, the affected score is invalid regardless of whether the resulting rule looks general.

Semantic scoring and diagnostics

The scorer compares normalized semantic values, not punctuation or terminal phrasing. It also records status correctness, expected abstention, proof requirements, provenance presence, and resource behavior. Exact-match text can remain a secondary metric for a benchmark that requires it, but a semantically correct result should not fail solely because a realizer chose “Yes.” instead of “yes”. Conversely, a plausible string with no valid derivation must not pass a symbolic capability gate.

Every failed case retains the actual result object or a bounded diagnostic projection of it. Failure categories distinguish parsing, binding, missing knowledge, missing method, invalid derivation, trust conflict, output mismatch, timeout, memory pressure, and infrastructure error. The classification directs work to the correct layer.

Contrastive and negative controls

Positive examples are paired with cases that rename entities, reverse directional relations, negate or remove premises, insert distractors, vary word order within the supported grammar, cross contexts, and request an unavailable capability. A rule learned from “mice fear wolves” must generalize through the variable binding and must stop applying if the type premise disappears. A lexical answer must change when the lemma changes. An abductive hypothesis must not become an asserted fact.

Unknown and abstention cases are first-class. If the package has no evidence, returning a structured unresolved subgoal is correct behavior. Evaluation therefore measures unsupported-answer rate and provenance completeness in addition to solved accuracy.

External comparisons

Comparisons with neural or hosted systems use frozen exported inputs and imported prediction files. The report names the external model, execution date, decoding policy when known, prompt or adapter, and unavailable metadata. ESLM’s offline property does not make its scores automatically superior; it changes the interpretation of reproducibility, provenance, and operational cost. Comparisons should present capability slices and resource regimes rather than one unqualified ranking.

Falsification criteria

The program is weakened if symbolic traces cannot predict failure, if package provenance cannot be followed to frozen evidence, if benchmark improvements require item-specific rules, if query-directed loading changes answers relative to eager loading, if agent outputs bypass promotion gates, or if broader language requires abandoning the explicit task and result contracts. Such outcomes must be reported as limitations or design failures, not hidden by aggregate success.

The complete evaluation regime is defined by DS010; implementation phases and acceptance gates are in DS011.

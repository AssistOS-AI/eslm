ESLM Documentation / CLI operations

One runtime contract across interactive, one-shot, batch, KB, training, and evaluation commands

The CLI is both an operator interface and a review surface. All question modes construct the same runtime and return the same semantic protocol. Administrative commands build or validate declarative artifacts; they do not smuggle a second reasoning implementation into scripts.

Ask one question

node src/cli.mjs ask "Can Penguin swim?" --kb quick
node src/cli.mjs ask "Define dog" --kb oewn-2025
node src/cli.mjs ask "Why might apologize?" --kb atomic-2020
node src/cli.mjs ask "QUESTION" --external-language-agent

The output is JSON. Read status and answer for the immediate result, then inspect input, query, taskFrame, plan, values, provenance, reasoning, usedKbVersions, unresolvedSubgoals, and model.memory. The WordNet and ATOMIC examples exercise source-specific declarative providers; the quick example exercises the canonical generic compiler and loader.

The general CLI uses the direct-first Language Agent profile by default; --external-language-agent states that choice explicitly and --no-external-language-agent selects the wholly offline route. The CLI always runs the offline runtime first. Only UNPARSED may trigger the external agent, whose output must pass schema and protected-anchor validation before the same runtime reparses it. One episode permits at most three proposals. A later proposal may receive bounded surface-validation errors or the narrow parser feedback that the previous CNL form remained UNPARSED; it never receives a symbolic answer, KB result, proof trace, expected value, or benchmark label. Assisted results expose the requested and declared operation, adapter, model, proposal and external-invocation counts, input digest, cache state, receipts, candidate, validation, and reparse status. Use --language-agent-model MODEL only for an intentional, separately reported override and --no-normalization-cache when neither reads nor writes of agent-derived text are acceptable. The current adapter invokes Codex with the local slug gpt-5.3-codex-spark; a successful local invocation does not establish that this slug is an OpenAI API identifier or that another Codex installation offers it.

Interactive presentation makes the assisted route difficult to mistake for a direct answer. An accepted case prints Original, Translation or Simplification, and Symbolic result on separate lines. A rejected case prints the original input, any proposed English, and the host-owned rejection reason. For example, Romanian Ce mai faci? may be translated to How are you?; the idiomatic mai is not counted as a comparative because no comparative construction is present, and the transformed English still has to match the generic symbolic operational-status intent.

Interactive and batch operation

Running node src/cli.mjs opens a session. Statements can extend only that session’s context, and later questions can refer to those entities and facts. Runtime commands expose selected KBs and memory state. The session does not alter canonical records or compiled packages. /normalize shows whether the external wrapper is enabled, its model and cache policy; /normalize on and /normalize off rebuild the wrapper without changing session facts or selected KBs. Pressing Tab completes slash commands, declared normalization and memory values, and available KB identifiers for /load and /unload. Completion only proposes text: it does not execute the command or alter ordinary-language input.

node src/cli.mjs run --input tests/fixtures/questions.txt --output /tmp/eslm-answers.jsonl

Batch mode reads input records and writes one result object per request. It is suitable for pipeline integration because answer text, semantic values, status, and evidence remain separately machine-readable. A failed case is written as a result rather than dropped from the stream. The default direct-first assisted profile applies independently to each record, so downstream tools can count direct cases, cache hits, external calls, rejected rewrites, and accepted normalized cases. Pass --no-external-language-agent when the batch must be wholly offline and independent of credentials or external service state.

Examples and the 4,096-case smoke regression

/examples
/examples 2
/examples 3 reproducible-review-seed
/smoke
/smoke 4096 reproducible-review-seed

/examples [PAGE] [SEED] renders 24 cases from the exact catalog used by /smoke. Page one and page two are different; each page states its range in the 4,096-case default catalog, the total page count, the template identifier, and the metamorphic relation under test. The stable default seed keeps page numbers reproducible, while an explicit seed changes nonce entities, classes, places, objects, and actions without changing the semantic obligations.

/smoke [COUNT] [SEED] executes the requested cases and defaults to all 4,096. Its 26 rotating templates cover class membership and retrieval, location paraphrases, state replacement, carried-object movement, temporal predecessor queries, possession and owner retrieval, abilities, safe Horn deduction, open-world controls, grammatical preference, a nonce multi-step Boolean entailment task, and a renamed categorical-opposition task. Typed tasks call the same public engine boundary as benchmark adapters. The command prints one representative case per encountered template with the input text, expected status and values, actual status, actual answer or preference scores, and actual semantic values. Every non-displayed generated case still contributes to the aggregate, and every failure is printed. A fresh offline generic-core plus QUICK runtime is used regardless of the session's selected KBs or enabled normalization wrapper, so session state and public knowledge cannot change the regression result or skip QUICK cases. Source-family tags describe structural inspiration and regression coverage; they are not copied benchmark sentences or public scores.

Knowledge-package operations

node src/cli.mjs kb list
node src/cli.mjs kb register /absolute/path/to/package/manifest.json
node src/cli.mjs kb unregister my-kb
node src/cli.mjs kb compile --input candidate/records.jsonl --output /tmp/my-kb-package \
  --id my-kb --version 0.1.0 --namespace my-kb
npm run kb:build
npm run kb:validate

kb list describes repository-managed and explicitly registered entries and their current package state. kb compile repeats the host canonical validator, sorts accepted records, writes inert JSON shards, and emits a hashed manifest; compilation does not register or promote the result. Registration opens and validates the manifest before storing a relative catalog reference; unregistration removes only the catalog entry and never deletes package data. Building recompiles repository-managed KBs from canonical records or frozen source archives. Validation opens manifests, checks package invariants, and performs provider checks. Build commands are trusted host operations; they never execute source or candidate text.

The current repository-managed list contains eight packages: quick, babi-v1.2-language, clutrr-kinship-algebra, oewn-2025, atomic-2020, geonames-2026, conceptnet-5.7.0-en, and world-relations-1.0. The bAbI and CLUTRR packages are intentionally small policy packages and contain no task answers. GeoNames, ConceptNet, WordNet, and ATOMIC are frozen public-source packages with query-directed loading. World Relations is an authored declarative ontology interpreted by the semantic compatibility core. kb show ID exposes each package's capabilities, source role, limitations, and validation state without loading all shards.

Training operations

node src/cli.mjs train prepare \
  --input tests/fixtures/training.jsonl \
  --namespace example-kb \
  --output /tmp/eslm-packet.json

node src/cli.mjs train candidate \
  --packet /tmp/eslm-packet.json \
  --output /tmp/eslm-manual-candidate

node src/cli.mjs train run \
  --packet /tmp/eslm-packet.json \
  --output /tmp/eslm-agent-workspace \
  --skill document-to-kb-builder \
  --dry-run

node src/cli.mjs train validate --model /tmp/my-kb-package

train prepare accepts only allowlisted training-visible record types and writes a frozen packet with a content hash and explicit target namespace. An omitted --output uses the operating-system temporary directory rather than recreating training/work/. Train-visible records are embedded as the assigned evidence container, while every source record still declares its media type, language, license, and content checksum. train candidate creates a manual candidate skeleton without launching an agent. train run creates an isolated workspace, computes the Stage A diagnostic baseline, and copies one named skill. Remove --dry-run only after inspecting the packet, assignment, workspace target, and selected skill. train validate opens a compiled package through the trusted host checks; the skill validator and kb compile are the preceding canonical-record gates. A successful agent exit, portable validation, compilation, or package validation does not promote its candidate. There is deliberately no train promote command until the reviewed version transition and publication policy are implemented.

Datasets, corpora, and caches

node src/cli.mjs dataset status --dataset babi-15-en-10k-v1.2
node src/cli.mjs corpus status
node src/cli.mjs benchmark status
node src/cli.mjs ask "Define dog" --kb oewn-2025 --memory-mb 256

Immutable downloads and extracted public data remain under ignored training/.cache paths. Dataset status reports the catalog entry, immutable archive, preparation manifest, split policy, and disk state for a named dataset. Corpus status distinguishes a cached source from a compiled package. Benchmark status is broader: it reports whether BLiMP, bAbI, CLUTRR, Entity Tracking, EWoK, Story Cloze, and SimpleQA have the exact local artifacts expected by their adapters. When protected EWoK artifacts are absent, status supplies the terms-acceptance and authenticated-download action; when they validate, status reports the cache without revealing its contents. Story Cloze status separately reports the validated form-delivered files, oracle boundary, recurring development protocol, sealed fresh experiment, and label-free test artifact. A cached source has bytes available; it does not prove that its adapter ran, its score is current, or its license permits redistribution.

A memory option affects package planning and cache policy and is reported in the result; it does not claim a hard process limit. The Language Agent normalization cache is different from a KB shard cache. Its entries are agent-derived text plus validation and process receipts, remain outside deployable packages, and retain assisted-route attribution even when no new subprocess runs.

Public probes, evaluation, and documentation

node src/cli.mjs benchmark catalog
node src/cli.mjs benchmark status
node src/cli.mjs benchmark probe --benchmark all
node src/cli.mjs benchmark probe --benchmark babi,entity-tracking --publish
node src/cli.mjs benchmark run --suite tests/fixtures/benchmark.jsonl --kb quick
npm test
npm run evaluate
npm run benchmark
npm run docs:matrix
npm run docs:check
npm run check

benchmark catalog describes intended task families. Its seven original public-adapter entries are joined by sixteen typed research registrations for LogicBench, IIBench, ProofWriter, PrOntoQA, SLR-Bench, LogicSkills, FOLIO, ProverQA, StepGame, SpaRC/SpaRP, SATBench, ZebraLogic, Defeasible NLI, alphaNLI/ART, ReClor, and LogiQA. Each entry carries queue stage, priority, capability contract, official source and paper, license or access state, cache identity, adapter state, evaluation state, and one explicit next action. All sixteen research registrations now have validated adapters and development or fresh receipts, but execution evidence still ranges from verified fresh solutions to complete task construction with no applicable method. Catalog inclusion by itself never claims a score.

benchmark status inspects cache, source identity, adapter state, evaluation state, rights, and remaining action. A validated executed source reports validated-frozen; absent and cached-unvalidated remain valid states for newly added or locally missing sources. benchmark probe executes the configured public adapters and combines their live measurements with frozen research receipts in latest-public-benchmark-probes.json. The public probe command is deliberately direct-symbolic and rejects --external-language-agent; its normalization-candidate percentage counts direct UNPARSED results without invoking an agent. A separately frozen suite passed to benchmark run --external-language-agent produces the assisted track and records special-analysis cases, cache hits, external invocations, accepted and rejected normalizations, route-specific accuracy, and route counts.

The full check runs unit and integration tests, deterministic KB validation, fixed-fixture evaluation, benchmark reporting, specification-matrix generation, documentation checks, and training-package validation. Commands that publish a report replace the corresponding generated result artifact; reviewers should compare protocol, sample policy, suite or source hash, runtime identity, package versions, route policy, and budgets before comparing scores. A locally validated protected source such as EWoK receives a denominator and a precisely labeled diagnostic; a source that is still absent or invalid remains not-run, never zero.

Operational failures

CLI syntax or invalid configuration exits nonzero and writes a concise diagnostic to standard error. A well-formed but unsolved language request normally returns a structured result, because inability to solve is part of model behavior rather than an operator error. Package checksum failure, unsafe training data, or an invalid promotion artifact is an operator error and stops the command. An unavailable Language Agent model, authentication error, timeout, malformed JSON, rejected anchors, exhausted proposal limit, or failed reparse produces an attributed normalization failure and cannot turn partial output into a solved result. Interactive mode remains open after such a failure.

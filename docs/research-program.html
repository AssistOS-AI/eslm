ESLM Documentation / Research program

System identity, research boundary, knowledge inventory, and review discipline

ESLM studies how far explicit language representations, reusable symbolic capabilities, declarative knowledge, and benchmark-guided program improvement can reproduce useful language-model behavior while preserving inspectability. This page contains the conceptual and operational material intentionally moved off the three-section home page.

The boundary that defines the project

The project separates three execution regimes. During training and knowledge construction, a coding agent may read a frozen, training-visible packet and propose normalized terms, assertions, rules, contexts, mappings, and provenance records. Those proposals are untrusted data and must pass schema checks, deterministic compilation, package audits, regression tests, evaluation, and an explicit promotion decision. The deployed runtime contains none of that machinery: runtime code is ordinary dependency-free Node.js; knowledge is JSON and JSONL; network access, agent calls, dynamic knowledge imports, source-string execution, and eval are forbidden.

The operator CLI is a separate regime and constructs the Language Agent-assisted normalization wrapper by default. It still runs the direct runtime first, sends text externally only after UNPARSED, and can be returned to the completely offline profile with --no-external-language-agent or /normalize off. The wrapper may only rewrite language and must return the rewrite through the same symbolic parser and reasoner; it is never part of the deployed offline-runtime claim.

This separation makes every promoted claim answerable: which source supported it, which compiler accepted it, which package version supplied it, which inference method used it, which rule produced a derived fact, and why the system abstained when a capability or premise was absent. A KB payload cannot silently gain executable authority, because it is never loaded as JavaScript.

What “language model” means here

The term denotes a system that interprets and constructs language by executing a model of linguistic forms, discourse state, world assertions, task operators, reasoning methods, and realization choices. The initial implementation intentionally supports a controlled English route before broader language induction. That route makes failures local: a result can distinguish unsupported wording from unresolved reference, absent knowledge, an unavailable inference method, a trust conflict, or a resource limit. Later statistical or induced components may rank alternatives, but they do not erase the symbolic contract or replace explicit verification.

The system is organized around reusable capabilities rather than benchmark labels. Retrieval, safe Horn deduction, induction, abduction, context handling, provenance traversal, planning, and realization are registered with preconditions and proof obligations. A benchmark case is converted into the same task representation as an interactive request. This prevents an adapter from becoming an unreviewed second runtime and makes comparison evidence meaningful.

Core, knowledge, and methods

The generic core owns representations and mechanisms that should remain valid across domains: normalization, controlled-language parsing, entity and variable handling, task frames, the capability registry, plan construction, safe rule execution, provenance, trust policies, budgets, caches, and structured result production. A knowledge base owns domain content: terms, lexemes, assertions, source-justified rules, contexts, provenance, mappings, and optional source-specific indexes. A method declares when and how a capability can be used. Keeping these responsibilities separate is the principal defense against turning one solved benchmark into hidden generic behavior.

The boundary is tested. A proposed generic rule that mentions a corpus label, benchmark answer, item hash, or domain constant fails review. A KB record without provenance fails validation. An unsafe rule whose conclusion introduces an unbound variable fails compilation. A package whose shard hash differs from its manifest fails opening. A query that cannot be completed yields a structured gap rather than a fabricated answer.

Review discipline

A useful review starts with the relevant DS files and then follows their contracts into source, package data, tests, and measured reports. It does not infer capability from a demonstration alone. A successful definition query establishes one routed WordNet behavior under a particular package and memory mode; it does not establish general lexical understanding. A passing controlled-English inference establishes the tested construction and reasoning path; it does not establish unrestricted English. Claims remain attached to their source split, package version, runtime version, budget, and scoring protocol.

The documentation explains the system from several viewpoints instead of compressing it into slogans. Architecture describes ownership and execution. Language describes representation and interpretation. Knowledge describes data and trust. Training describes agent authority and artifact gates. Evaluation describes what evidence can and cannot justify. Temporary scores and access actions live in generated or current-status artifacts; the DS files remain the contractual authority for stable behavior.

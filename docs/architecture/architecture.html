ESLM Documentation / System / Architecture and runtime

Trusted runtime, declarative knowledge, bounded dispatch, and evidence-bearing results

This chapter describes the system's trust regions and functional responsibilities. Trusted processing nodes define language interpretation, planning, retrieval, reasoning, verification, caches, and result construction. Knowledge packages contribute only validated data. Training agents propose candidates outside the deployed runtime. Every transition between these regions has a typed envelope and an authority gate.

Trust regions and execution families

The operator boundary validates commands and creates a configured runtime. Language processing applies the English-only gate and converts continuing utterances into symbolic queries, session assertions, or explicit gaps. Knowledge processing validates canonical records, compiles deterministic shards, opens manifests, routes queries, and projects supported records into reasoning indexes. Planning and reasoning publish capability contracts, build the current bounded single-goal audit skeleton or typed task, dispatch allowlisted operations, and execute finite methods. The training boundary prepares isolated workspaces and may invoke a Coding Agent only through an explicit training operation. That authority is separate from the operator-side Language Agent, whose only role is an untrusted translation proposal after likely-non-English rejection or English simplification after local recovery remains UNPARSED.

Language recovery is an operator-side coordination path around the same semantic authority gate. A bounded local diagnostic rejects likely non-English input without translating it. Explicit request force is assessed independently from the tentative direct result, preventing instruction text from becoming committed session assertions. When no request plan applies, deterministic local English strategies inspect eligible direct outcomes and propose alternatives from visible structure. Equal Semantic IR preserves the direct route; a changed interpretation is query-local. The general CLI composes a disclosed external proposal strategy by default, and every candidate returns through the same English parser and reasoner. Neither recovery path can call a reasoning method directly, inject knowledge, or use answer success to choose wording.

These layers are not interchangeable. The CLI may select a KB, but it cannot bypass package validation. A KB may contain rules, but it cannot introduce an inference operator. A training skill may propose a generic-core change, but it cannot promote or execute that change. A reasoning method may request indexed data, but it must obey the configured cache and shard budget.

The CLI coordinator submits visible input through the English gate and receives a typed local result. It may accept that result unchanged, preempt an accidental assertion parse with a query-local explicit request plan, or submit one parse-only-selected local candidate back through the same runtime. A direct SOLVED or PARTIAL changes only when that candidate has different Semantic IR. The external Language Agent is an untrusted proposal strategy: likely non-English input may request translation, while unsupported English may request simplification after local recovery. A validated KB contributes data to the runtime, never executable behavior, and every route returns one structured result through the coordinator.

Processing nodes and trusted strategies

The runtime is being unified as a directed graph of typed processing nodes. A node names one stable responsibility and protocol. A strategy is one statically trusted implementation of a selectable node, with an exact version, finite work, evidence role, and witness. Only coordination nodes compare candidate proposals. Parsers, safety checks, reasoning executors, proof verifiers, and package validators are authority gates or semantic processors; their decisions cannot be replaced by confidence voting.

All 24 local language-approximation families are real coordinated strategies. Exact selections also gate request planning, query focus, relevance features, reasoning methods, and result construction inside their current instrumented-local owners. Ordinary method planning and witness verification now have closed bounded owner envelopes; retrieval, failure grounding, method planning, and verification remain non-selectable until they cross the shared coordinator boundary. The Logical processing architecture separates request flow, named protocols, execution resources, and implementation reference. The Processing-node strategy architecture then zooms into descriptors, selection, coordination, receipts, and migration states.

Generic core versus knowledge packages

The generic core contains domain-independent operations: token normalization, construction matching, variable binding, task construction, capability selection, safe Horn unification, proof assembly, provenance traversal, context checks, trust policies, result realization, and bounded storage. It can know what an assertion is and how a rule is executed. It must not know that penguins swim, what “dog” means in a particular lexical resource, or which commonsense consequences accompany apologizing.

A KB package contains terms, lexical forms, assertions, rules, contexts, provenance, mappings, and source-oriented indexes. Its manifest identifies the package, schema, version, compiler, source hash, record counts, shards, and shard hashes. Because package content is declarative, loading it does not grant it filesystem, process, import, or network authority. Provider-specific compact formats such as the current Open English WordNet and ATOMIC packages remain data and are accessed by trusted adapters.

Task planning and method selection

A capability descriptor states the semantic operation it advertises, accepted inputs, preconditions, result type, proof kind, bounds, and cost model. These fields are reviewable contracts for trusted methods. They are not proof that the current planner checked every precondition or invoked the callback stored beside the descriptor.

The ordinary-language path is intentionally narrower than the target planner. Its task-frame node creates one goal. Its planning node maps the reasoning tag to one advertised capability, applies the exact method allowlist, selects deterministically, and emits the fixed audit sequence OBSERVE → DERIVE → VERIFY → CONSTRUCT. A closed execution envelope then runs the reviewed retrieval, safe-Horn, configured-induction, abduction, or temporal-predecessor binding. A separate bounded authority gate replays the returned support against host-owned facts, rules, policy, or history; only an accepted strict witness can authorize answer construction. The plan still does not build an AND/OR graph, compare costs, or delegate through the common coordinator.

Typed tasks use a second bounded path: an allowlisted operation selects one method descriptor and trusted executor. This is how finite state, relation, spatial, categorical, Boolean, countermodel, and other typed methods run. The scalable Boolean method is therefore a real SAT-backed executor, but its existence does not imply general SAT planning. Multi-goal decomposition, alternative-branch execution, declarative domain-plan interpretation, and planner-wide precondition and budget enforcement remain target work. An unsupported operation returns a structured method gap; neither path falls back to plausible text.

The Entity Tracking adapter uses the complementary structured-task entry point. It emits complete-container-contents with no label and compiles the source's box and verb syntax into finite-relation-state-program-v1. The runtime selects method:core:container-state-transitions, which sees only typed contains assertions, transfer, add, and remove operators, and a relation query. It bounds subjects, transitions, and values and returns the final semantic values plus a trace. This method is generic because the adapter-owned source words, subject identifiers, relation values, and item names can all be replaced without changing the algorithm. The official span remains in a host-only oracle used after execution.

Typed relation composition

The relation-algebra entry point accepts a graph of typed edges, entity features, two query endpoints, and one declarative algebra. It validates every identifier and relation reference, adds only inverse edges declared by that algebra, and explores paths under explicit depth and state budgets. A dynamic composition table reduces the edge-class sequence. The result is refined into an output relation only when the target endpoint's features support that refinement. The trace retains every asserted or inverse edge and the nested composition witness.

CLUTRR uses this route through structured source fields, with route labeling that keeps it distinct from controlled-English execution. The adapter owns graph extraction and source schema validation. clutrr-kinship-algebra owns the licensed relation inventory, gender-sensitive refinements, inverse table, and composition table. Trusted code owns traversal, composition, ambiguity, inconsistency, and budgets. If two source cases present isomorphic typed evidence but request distinct blood and in-law labels, the runtime returns ambiguity; adding an item ID branch would violate the method's input semantics.

World compatibility and context preference

Semantic compatibility converts bounded text into ontology-declared unary, binary, proposition, comparison, change, possessive, material, action, and numeric frames. It normalizes argument order and polarity, derives only declared inverse relations and implications, compares target frames with context frames, and emits signed evidence. world-relations-1.0 owns the reviewed English constructions and their semantic mappings. ConceptNet may add independently sourced relation evidence through the same provider-neutral interface. Neither source is allowed to contain an EWoK row or preference label.

The EWoK adapter uses that general operation twice: it holds one target fixed, scores it with each visible context, and requires the designated context to receive a strictly higher score. A tie is a failed preference, not an invitation to choose a candidate position. This local scalar protocol is intentionally described as a symbolic diagnostic rather than the benchmark's official language-model probability protocol.

Narrative continuation selection

The narrative compiler represents each context sentence and candidate ending as a bounded event frame: content terms, predicate candidates, named participants, pronoun groups, polarity, modality, and tense. The continuation method calculates declared structural features such as participant continuity, content bridges, tense agreement, polarity conflict, and lexical novelty. Selected providers can add bounded causal, goal, event, social, state, or contradiction evidence. Every feature records its value, weight, contribution, and provenance.

The selector returns a defeasible candidate only when its score exceeds the declared minimum margin; otherwise it abstains. Story Cloze's development-visible feature policy lives in the adapter with calibration provenance. Candidate identifiers come from visible content rather than answer positions, and the host-only correct ending never enters the task. This makes the computation reviewable without inflating a bounded continuation ranker into a claim of unrestricted narrative understanding.

Factoid routing

A recognized factoid question becomes a provider-neutral frame containing WH type, construction, relation surface, direction, subject when recoverable, and conservative provider paraphrases. Every loaded provider is consulted independently. Equal semantic answer sets are merged with all provenance and the weakest successful epistemic status, so an agreeing defeasible edge cannot be upgraded to SOLVED. Distinct answers or provider-declared ambiguity produce AMBIGUOUS. Provider order never decides the answer. Each optional provider call is a contained begin/use/end transaction; any stage failure discards that provider's tentative contribution, records a bounded diagnostic, and lets the remaining providers continue. When no provider responds, the runtime returns a structured factoid knowledge gap rather than mislabeling the recognized question as unsupported language.

This route lets GeoNames, ConceptNet, Open English WordNet, and other independent packages contribute to SimpleQA-like questions without importing a SimpleQA reference answer. It improves the boundary between parsing and knowledge coverage; it does not claim encyclopedic completeness or replace the benchmark's semantic grader.

Reasoning and proof evidence

Retrieval returns the record identity and provenance that directly support a value. Deduction recursively satisfies rule premises, maintains substitutions, prevents unsafe variable escape, and records rule depth. A derived value cites the rule and the supporting facts or subproofs. Negative conclusions require explicit negative evidence or a declared closed-world policy; absence alone is not ordinary proof of falsehood.

Inductive conclusions are hypotheses supported by observations and must be labeled as learned, scoped, and defeasible. The current bAbI policy is declarative KB data: it names the color value domain, the implicit query trigger, support and coverage thresholds, and latest-member selection. The core owns only the reusable induction mechanism and refuses to invent a policy for an undeclared property. Abductive conclusions are explanatory candidates and must not be represented as established facts. This distinction survives realization so a human answer cannot conceal the epistemic status of its underlying result.

Temporal predecessor evidence contains the previous and boundary events from ordered session history. Container-state evidence is an execution trace rather than a Horn proof. Each result names the method it used, which lets reviewers distinguish retrieval, deduction, induction, state-history lookup, task-program execution, and abstention even when two methods happen to produce the same surface answer.

Memory, routing, and caches

Small packages may be loaded eagerly. Large packages use manifest metadata and query-derived routing keys to select only relevant shards. The cache has an explicit memory policy, reserve, byte target, and eviction behavior. Cache occupancy and loaded-provider information are exposed in runtime metadata. A soft memory target is not advertised as a hard operating-system guarantee.

Routing is part of correctness. If a key cannot map conservatively to all potentially relevant shards, the loader must broaden the selection or report the limitation; it must not omit evidence merely to remain fast. Paths from manifests are resolved against an allowlisted package root, and hashes are checked before records are trusted. No package field becomes an import specifier.

The result protocol

eslm-runtime-result-v1 is stage-dependent. Every text result reports protocol, status, answer, session and episode state, language route, selected, consulted, and used KB versions, unresolved subgoals, and memory policy. Normalized input, parsed query, task frame, selected plan, semantic values, provenance, and reasoning method appear only when execution reached the stage that can construct them truthfully. Consequently an early UNPARSED result can omit all of those semantic-stage fields. SOLVED means the requested contract was met. Other statuses distinguish missing knowledge, missing capability, ambiguity, underdetermination, conflict, unsupported output, and exhausted resources.

For supported inability statuses, the conditional grounding node may attach an eslm-grounding-bundle-v1 after the primary result is complete. It searches bounded loaded-model or provider indexes for related records while leaving status, answer, values, answer provenance, and contributor-only usedKbVersions unchanged. Every bundle says answerSupported: false and carries per-source search receipts. The current implementation never starts this extra retrieval after RESOURCE_LIMIT. See Grounded failure and related evidence for the field-by-field contract.

An assisted result adds the original direct failure and a normalization object containing trigger, exact model, cache attribution, digests, bounded process receipt, candidate, validation, and reparse status. language-agent-normalized, language-agent-normalization-failed, and language-agent-normalization-rejected are visible route distinctions. A textual answer is only one view of this object. Evaluation scores semantic fields and diagnostics, not terminal decoration. Batch mode writes one structured result per input. Interactive mode maintains session context but uses the same engine and result protocol.

Security and determinism

The runtime has no dependency on Language Agent, an LLM service, or network data. It does not execute strings from documents, benchmarks, manifests, or shards. Canonical validation rejects unknown record types, invalid identifiers, dangling references, unsafe rules, missing provenance, and malformed contexts. Compilation sorts records and writes stable JSON so equal inputs and compiler versions produce equal content hashes.

The external proposal executor is intentionally outside this deterministic claim. It runs in a new empty temporary directory with a read-only sandbox, no approval escalation, ignored user configuration and repository rules, disabled tools, a bounded environment, and a strict response schema. Standard output and error are each capped at 2 MiB; timeout or overflow escalates from SIGTERM to SIGKILL after 250 ms and has a final bounded settlement window. Response JSON is limited to 1 MiB and cache JSON to 4 MiB, both checked before parsing. Its output is untrusted and never executed. Host validation requires one-to-one protected-anchor coverage and English content preservation for simplification. Translation also needs target-English assessment and direct reparse, but open-class equivalence remains UNVERIFIED_NORMALIZATION without an independent reviewed source-language profile. Cache keys bind model and policy versions, and cache hits remain assisted evidence. Local successful receipts establish an operational Language Agent CLI observation only; the project does not infer API support from them.

Determinism includes failure behavior in the direct profile: the same package set, task, runtime version, budgets, and session state must produce the same plan choice and semantic result. Timestamps belong in build or external-process receipts where they describe an event; they do not participate in canonical shard identity.

Reviewer trace and implementation map

For a runtime change, begin at the task contract, identify the owning processing node, follow every typed edge, and verify both successful and exceptional paths. For a package change, compare source identity, canonical validation, compiled integrity, routing coverage, proof provenance, negative controls, and regressions. For a new method, inspect its descriptor, dispatch boundary, bounded execution, witness gate, failure form, and domain-independence. For a strategy change, distinguish catalog state from exact selection and actual execution; inspect scheduling, preallocation, result validation, correlation, candidate arbitration, receipts, and leave-one-out behavior. For grounding changes, verify topic-role filtering, unchanged primary fields, ranking, coverage receipts, provider-order invariance, and the resource guard. For language recovery, verify the English gate, local-first simplification, direct translation-proposal routing, protected meaning, reparse, rollback, disclosed assisted default, and explicit local override.

The implementation map is deliberately secondary: runtime composition lives under src/runtime/, language nodes under src/language/, strategy coordination under src/strategy/, knowledge processing under src/kb/, and planning and methods under src/reasoning/. The exact contracts are maintained in DS002, DS006, DS008, DS009, DS013, DS022, and DS027.

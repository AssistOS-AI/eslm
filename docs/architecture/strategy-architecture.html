Alternative processing strategies and meta-rational coordination

A processing node is a stable typed responsibility in ESLM's logical graph; a strategy is one statically trusted implementation of a selectable node. All 24 local language-approximation families now run through a sealed registry and deterministic coordination node. Exact allowlists also gate request planning, query focus, relevance features, reasoning methods, and result construction inside their existing owners. DS027 carries this foundation toward one reproducible cross-stage graph and a separate compiler graph without giving knowledge packages or runtime input authority to load code.

Processing nodes, strategies, coordinators, and gates

A processing node owns one input envelope, output envelope, semantic responsibility, resource contract, failure vocabulary, and receipt. A strategy is a reviewed implementation of one selectable node. The host binds a descriptor to its executor before work begins, seals the registry, and later allows policy to select only exact registered identities. The language registry already enforces this lifecycle for its 24 families. The common registry accepts only descriptors marked coordinated; catalog entries marked instrumented-local or planned cannot masquerade as coordinated executors. This supports alternative implementations, ablations, and clear research ownership without directory scanning, package installation, dynamic imports, callbacks from JSON, or code supplied by a corpus.

Only a coordination node combines votes over typed candidates. Parsers, schema and safety checks, reasoning executors, witness verifiers, result validators, and package compilers are processors or authority gates. They return accepted output, rejection, or a typed gap; popularity cannot replace their contracts. A method-planning coordinator may rank applicable method plans, but an executed method returns a semantic result and witness rather than an answer vote.

Declarative knowledge remains on the other side of the authority boundary. A KB may contain facts, lexical forms, relation systems, source-backed rules, trust metadata, or a schema-permitted compatibility reference to an exact strategy identity. It cannot provide an executor, module path, command, arbiter, resource limit, or verification bypass. A missing exact identity is a visible compatibility or profile error; the host never searches for similarly named code.

The typed input may contain validated KB evidence, but it remains data. The policy gate resolves an exact allowlist from the host-owned catalog. The sealed registry provides the matching trusted executors in canonical order. The coordinator preallocates finite work, invokes and validates each executor, and emits a bounded stage receipt beside its output. At the present checkpoint this complete path runs the 24 language families. Request, focus, relevance, reasoning, and construction selections are real gates whose owner modules still perform the stage work. Retrieval and failure grounding retain local owners; method planning and verification now expose bounded owner envelopes, but all four remain non-selectable integration points.

The canonical runtime dataflow

DS027 defines one ordered processing graph so techniques do not call each other through hidden control flow. Each node receives immutable typed output from its predecessors, runs its selected implementation or strategies under one contract, validates its result, and advances an explicit edge. Coordination nodes arbitrate candidates; ordinary processors and authority gates do not. A language strategy cannot query the KB to discover which rewrite produces an answer. A retrieval strategy cannot call a reasoner recursively. A constructor cannot repair an invalid witness. The external Language Agent is logically a proposal strategy at the language node; its subprocess executor stays outside the deployable registry and can only emit untrusted English that returns through the direct parser.

The current request planner is still an instrumented-local owner, so its scheduling is explicit but not yet the final cross-stage coordinator implementation. After the direct attempt it checks bounded request force before local approximation. An accepted plan restores the incoming session snapshot and skips language alternatives. Otherwise UNPARSED and UNKNOWN enter candidate inspection; direct SOLVED or PARTIAL changes only for a structurally licensed candidate with different Semantic IR. Coordinator migration must preserve this safety order and expose the diagnostic as a typed transition.

Descriptor, run result, candidate vote, and receipt

Four records answer four different review questions. The descriptor says what a strategy is allowed to do. The run result says what happened during one invocation. At a coordination node only, a vote says how one strategy supports or opposes one canonical candidate under one confidence meaning. The receipt reconstructs selection, allocation, execution, arbitration, and failure across the node, stage, or pipeline. Keeping them separate prevents a descriptive catalog entry from being mistaken for successful execution and prevents a reasoning result from being misread as a popularity vote.

Canonical scheduling and finite resource allocation

The implemented StrategyRegistry stores an exact descriptor/executor pair and returns entries in canonical stage and strategy-identity order. It accepts only descriptors marked coordinated; an instrumented-local or planned inventory entry cannot masquerade as an integrated executor. Both coordinator APIs validate an optional exact allowlist and freeze at most one explicit invocation slot for every selected identity before any executor runs. The asynchronous runStrategyStage starts every funded independent executor before awaiting their shared stage barrier, contains rejection or invalid output per branch, and assembles results and arbitration in canonical identity order rather than completion order. An unallocated identity remains visible as resource-limit and is never invoked. Its receipt deliberately contains no timing or completion-order fields.

The synchronous runStrategyStageSync uses the same canonical frozen allocations but invokes one identity at a time. The current deployed local-language path calls this synchronous API for all 24 approximation families, so deployed language execution remains sequential until that owner is explicitly migrated. Owner-specific work also remains separate: the language owner divides edit-distance evaluations only among its three declared consumers and records actual use in their outputs. The arbiter deduplicates byte-equivalent canonical outputs and counts only the strongest typed evidence inside each declared correlation group. Equal top support is ambiguous. Concurrency and resource consumption add no confidence: only independent correlation groups carrying validated evidence may contribute separate support under the stage's confidence semantics.

The complete scheduler is deliberately stronger. It evaluates typed preconditions, dependency and conflict graphs, and mandatory gates before any executor runs. It reserves parser, safety, verification, and result-validation work first, then allocates the remainder under execution, stage, profile, and descriptor ceilings. DS027 specifies deterministic largest-remainder allocation with exact-identity tie breaking and explicit carry-forward policy. One fast callback cannot consume another strategy's opportunity, and unused work cannot move opportunistically because a cache happens to be warm.

The existing eslm-work-policy-v1 already gives quick, balanced, deep, and exhaustive-bounded exact finite limits for heuristic candidates and reparses, Horn work, provider fan-out, and grounding. It also validates an inventory-only preset and exact stage-to-identity execution selections. The next integration gate adds canonical stage budgets, per-strategy reservations and maxima, allocation weights, mandatory gates, and the corresponding digest to that policy surface. A descriptor ceiling remains a hard maximum; a profile may narrow it but never expand it.

Confidence directs work; proof establishes claims

Confidence is typed by the question it answers. Interpretation confidence estimates whether a candidate preserves the user's meaning. Request-plan preference ranks alternative obligation structures. Retrieval relevance ranks which records deserve bounded work. Method applicability estimates whether a semantic executor fits the task. Extraction confidence prioritizes a source-derived candidate for review. None of these quantities is automatically a probability that an answer is true, and values from different confidence kinds cannot be averaged without a separately specified conversion.

Safety and type checks are authority gates, not small negative votes. Repeating one cue through several proposal strategies in the same correlation group cannot manufacture independence; a candidate arbiter counts at most the strongest equivalent support from that group. A close margin yields ambiguity or a stage gap. For reasoning, one independently verified strict witness may authorize a strict answer. Agreeing proofs merge witnesses and provenance rather than confidence points. Defeasible evidence stays defeasible, strict disagreement remains a conflict, and absence of proof from an incomplete search never becomes proof of falsehood.

Profiles, allowlists, and operator inspection

The CLI intentionally separates inspection from execution. --strategy-preset all|language|retrieval|reasoning|construction filters the inventory shown by /strategies; interactive /strategies PRESET changes that view. A named preset never enables, disables, or reorders a strategy. This makes focused architectural inspection safe: looking at the reasoning inventory cannot accidentally turn off language or grounding.

In the inventory, executionEnabled means that an exact-selection-enabled identity is admitted by the current policy. It is not a claim that the strategy ran in the last question. Conversely, catalogued-not-policy-gated can describe a retrieval or grounding owner that still runs in the product path but cannot yet be controlled through DS027 selection. Stage receipts, owner receipts, and the result route are the execution evidence.

--strategy-select 'STAGE=ID[,ID];STAGE=ID' is the execution control. Interactive /strategy STAGE=IDS applies the same exact allowlist and /strategy clear removes all exact overrides. The CLI rejects unknown identities, wrong-stage identities, duplicate stage assignments, empty selections, planned entries, and any attempt to omit the mandatory direct parser or function-word exclusion strategy. Paths, URLs, package names, code strings, commands, and callbacks are not part of the syntax.

# Inventory only: execution is unchanged
--strategy-preset retrieval

# Exact execution selection
--strategy-select \
  'runtime.evidence.assess=strategy:retrieval:focus-term-cooccurrence@1,strategy:retrieval:typed-answer-bridge@1'

# Interactive inspection and selection
/strategies reasoning
/strategy runtime.reason.execute=strategy:core:safe-horn-deduction@1
/strategy clear

Exact allowlists currently gate language approximation, request planning, knowledge focus, evidence assessment, reasoning execution, and result construction. The 24 language families execute through the common coordinator. The other selectable stages are instrumented-local: their existing owner modules honor the allowlist and expose it in receipts, but do not yet delegate their work to the common stage runner. Retrieval-frontier execution, failure grounding, method planning, and verification stay visible but non-selectable until that integration is real.

The work profile controls how much finite effort is available. Exact strategy selection controls which reviewed alternatives participate. Both belong to execution identity: a wider work profile may complete a frontier, while a different exact allowlist may legitimately consider different reviewed semantics.

How a researcher adds or improves one strategy

  1. Define one generic typed problem and show why the existing strategy set cannot represent it cleanly.
  2. Develop the candidate outside default registration. Keep source vocabulary, benchmark labels, expected answers, and record identities out of its control flow.
  3. Publish its descriptor, executor, validator, finite resource model, confidence meaning, witness, and bounded receipt.
  4. Add renamed and nonce tests, reordered and irrelevant evidence, a meaning-changing contrast, invalid-output and exception containment, and explicit budget exhaustion.
  5. Register it statically and select it explicitly in a research configuration. Compare the baseline, the new strategy, and per-strategy ablations on the same frozen inputs.
  6. Measure applicability, calibration, conflicts, incremental benefit, resources, end-to-end effect, and any regression in abstention, provenance, or proof validity.
  7. Promote it into a product profile only through review. A semantic change creates a new exact version; retirement leaves a migration receipt.

Deployed execution never invents a strategy, edits a weight, changes a threshold, or promotes itself. Runtime failures can be clustered offline into research proposals. DS023 through DS026 use this control plane for relevance, scope-safe language, verified synthesis, and grounded product evaluation. DS028 adds rights-aware discovery of missing nodes, gates, strategies, edges, and data fields from inert task evidence. Researchers can therefore work on one difficult surface while preserving a common execution and evidence discipline.

Benchmark identity for a selectable system

A benchmark result is reproducible only when it binds behavior to the strategy configuration that produced it. Every row claimed as current therefore carries a bounded eslm-benchmark-strategy-configuration-v1 snapshot. It records the content-addressed built-in catalog, requested and effective work-policy profiles, inventory preset, exact stage allowlists, configured arbiter identities and policy digests, and a digest over the complete configuration. An adapter-local benchmark records its explicit bounded adapter state and digest instead of pretending that it used the ordinary runtime policy.

A benchmark row aggregates many executions, so it cannot embed one convenient case receipt as evidence for the whole denominator. Actual coordinated activity is summarized per stage as eslm-benchmark-strategy-stage-receipt-summary-v1: execution count, complete and incomplete counts, a bounded uniqueReceipts ledger of receipt digest, occurrence count, and completeness, plus a digest over the summary. Configured arbiters are listed as configuration; only the stage summaries and underlying receipts show execution. Stored rows lacking this strategy snapshot remain historical or reporting-incomplete until rerun.

Implemented foundation and completion gate

The repository now contains a typed descriptor and result validator, an exact-identity registry that freezes every accepted descriptor, a sequential synchronous stage runner, a genuinely concurrent asynchronous runner with canonical completion-independent receipts, advance invocation-slot allocation, bounded per-branch failure containment, a correlation-aware confidence arbiter, a built-in cross-domain inventory with explicit implementation states, a machine inventory with selection digest, inventory presets, exact execution allowlists, and focused barrier, completion-inversion, zero-allocation, failure, renaming, and nonce tests. The 24 real language-family executors use the synchronous registry path and remain sequential. Request planning, focus, relevance, reasoning, and construction honor exact allowlists inside their established bounded owners.

The refactor reaches the complete DS027 architecture when the common coordinator owns every declared runtime extension point; the remaining selectable owners migrate from instrumented-local to coordinated; retrieval, method planning, failure grounding, and verification become genuinely selectable; dependencies, mandatory gates, multi-dimensional preallocation, and independent verification are integrated; compiler strategies use their separate registry; result accounting includes registry/profile/work/package/input digests and complete cross-stage receipts; and benchmarks are rerun under frozen exact selections. Until those gates pass, the page identifies the coordinated language slice, the real local gates, and the future extension points separately.

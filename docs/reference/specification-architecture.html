How the DS set is divided so changes remain local

The specifications are organized by independently changing contract surfaces. Stable rules stay in DS files; benchmark inventory and results stay in typed catalogs and generated receipts. This removes the former pattern in which one adapter addition forced edits across language, CLI, storage, roadmap, and status specifications.

Normative stability decreases from left to right. Generated evidence may change after every run without changing the contracts that define how the run is interpreted.

What was removed from the old boundaries

Language Agent process and retry details are assigned to DS013 rather than the direct-language DS. Document-specific meaning remains in DS014, while generic source authority, canonical records, physical compilation, routing, caches, learning, and security remain in DS016, DS005, DS019, DS020, DS021, DS004, and DS009. Reasoning algorithms are assigned to DS015 rather than architecture or planning. DS027 owns how alternative trusted implementations are described, selected, bounded, coordinated, and audited; it cannot redefine method semantics or grant executable authority to knowledge. DS028 owns dataset-guided hypotheses and their rights, visibility, projection, contamination, ablation, and promotion lifecycle; it cannot turn trajectories into policies or bypass DS027. DS029 owns the exact descriptive hierarchy into which implemented and planned processing points are named, typed, connected, and validated. It does not claim that every cataloged node executes through the common coordinator, and a DS028 hypothesis does not become a DS029 catalog entry merely because several strategies voted for it. Adapter shapes and split isolation belong to DS017, while scoring and reports belong to DS010. Current adapter lists and post-reset implementation narratives remain outside roadmap and documentation contracts.

Decision and open-question rule

Every retained numbered entry is an actual Question. A settled choice uses Response: and records rationale that constrains future implementation. A contract-shaping unresolved choice uses Options:, identifies concrete alternatives and discriminating evidence, and leaves the affected behavior unimplemented until selection. The Research decisions page indexes these normative open questions and separately records operational choices that do not change a generic contract; it cannot replace the DS owner. Benchmark blockers and proved limits live on Exceptions and issues, while changing counts and percentages live only in generated result artifacts.

Expected change locality

Adding a benchmark normally changes its catalog entry, source manifest, adapter, tests, source-specific receipt, HTML protocol page, and generated public report. Adding a KB package changes its source receipt, canonical records or source compiler, package files, tests, KB inventory, and generated status. Adding a reasoning method changes its executor, descriptor, DS015, focused and metamorphic tests, and reasoning documentation. Adding an alternative implementation under an existing typed strategy boundary changes its descriptor, implementation, validator, profile, ablations, and DS027 evidence without rewriting the semantic owner. Adding a DS028 discovery source changes its rights registry, inert projection, contamination ledger, research receipt, and source-specific analysis evidence; it does not change runtime behavior or DS029 catalog state until a separate generic proposal completes promotion. A DS029 edit is appropriate when an exact node, circuit, edge, packet family, authority class, implementation state, or resource dimension changes; a new analysis receipt alone is not such a change. Cross-cutting DS edits are justified only when the shared interface really changed.

The generated specification matrix is the canonical index. The explanatory logical processing architecture separates the four architectural planes. Processing-node strategies maps DS027 to trusted implementation selection and coordination; dataset-guided graph research maps DS028 to the evidence-to-hypothesis lane; and DS029 defines the exact descriptive circuit and packet catalog against which current implementation state and proposed changes are reviewed. Execution, hypothesis, and catalog membership are three different claims.

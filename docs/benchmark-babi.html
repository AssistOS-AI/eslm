bAbI: explicit state, deduction, and induction tasks

bAbI is a collection of 20 synthetic question-answering task families. Its short stories isolate operations such as following state changes, combining supporting facts, deduction, induction, counting, path finding, temporal order, and motivation.

What the current run tests

The latest development run executes every one of the 200,000 questions in all twenty official English 10k training files: 10,000 questions per family. It is comprehensive for that train-visible denominator, not a sample and not an untouched official test score. The test files remain outside this development execution.

The twenty families exercise single-, two-, and three-fact state tracking; conjunction; event-role projection; yes/no state questions; counting and set enumeration; elementary coreference; temporal order; positional vectors; path finding; size and containment relations; class-property induction; and motivation. The adapter maps these documented surfaces to typed operations. The registered core receives neither the family number nor the expected answer.

The finite episodic-world method

method:core:finite-episodic-world folds ordered movement, acquisition, release, transfer, and relation operations into a finite world. Other accepted operations add immutable event roles, graph edges, vector constraints, class memberships, properties, and motives. The task also carries declarative inverse relations, vector mappings, transitive relations, induction selection, and motive-to-goal policy. Relation spellings and entity names have no special meaning inside the executor.

A query asks for one typed operation: state, predecessor, membership, count, contents, event role, relation closure, vector membership, path, order, induced property, motive goal, or event cause. The result names every operation that supports its semantic values. An independent verifier rebuilds the episode, recomputes the complete answer, and checks those operation references. Full entity, predicate, value, relation, and ordering renames; semantic reversals; unknown cases; and witness tampering are tested independently.

Current ESLM protocol

The adapter reads the visible story and question, constructs the typed episode, and keeps the declared answer and supporting-line identifiers in a host-side oracle. The scorer joins the oracle only after execution. A case is correct only when the semantic value set matches; a plausible explanation or a witness copied from the oracle is not accepted.

The complete train-visible run produces 199,872 single-label matches from 200,000 cases, and all 200,000 execution witnesses replay. Tasks 1–4 and 6–20 are each 10,000/10,000. Task 5 is 9,872/10,000 plus 128 explicit AMBIGUOUS results. This page records the stable scope and interpretation; the home page renders the replaceable numerator, denominator, status counts, and percentage from the public JSON report.

Why 128 Task-5 questions are not tie-broken

Each affected visible story contains at least two transfer events with the same requested agent, recipient, event type, and theme role but different transferred objects. The question asks what the agent gave the recipient, without a visible temporal boundary, ordinal, uniqueness condition, or support-line selector. Both objects satisfy the typed query. The sound output is therefore the complete two-or-more-value set with AMBIGUOUS.

This is not merely a preference for conservative behavior. The 128 cases form 23 alpha-renamed structural signatures. Five signatures have contradictory official selections. For example, the same visible pattern containing one direct transfer of value 0 and a later direct transfer of value 1 selects value 0 in nine rows and value 1 in twenty-seven. Other signatures similarly contradict always-first, always-latest, always-prefer-direct-transfer, and always-prefer-pass policies. A deterministic rename-invariant function of the visible query cannot reproduce both labels. Single-label scoring becomes well-defined only if the task exposes a temporal or ordinal selector, accepts every satisfying theme, or explicitly makes the supporting-line annotation visible input.

Why the evidence remains useful

Comprehensive execution establishes delivered-family coverage, while renamed entities, changed properties, removed premises, reordered independent operations, meaning reversals, unknown cases, and witness tampering establish semantic generality. The result still remains development evidence because the official training stories and their failure clusters were available while the implementation changed.

Executable Symbolic Language Model

A deterministic language runtime with inspectable answers, evidence, and capability boundaries

ESLM parses controlled English, constructs explicit tasks, runs trusted symbolic methods over declarative knowledge packages, and returns structured results. Its substantial finite reasoning machinery provides a reliable foundation for progressively broader language interpretation, knowledge coverage, and planning, with every expansion tied to executable acceptance evidence.

QuestionCurrent answer
Does the deployed runtime call an LLM?No. Runtime inference and local heuristic recovery are deterministic, offline, and use no network or child process. The general CLI may invoke a separately configured Language Agent only after local recovery leaves UNPARSED and the operator explicitly opts in.
What is implemented?Controlled-language parsing, typed task records, bounded capability dispatch, direct retrieval, safe Horn closure, several finite logic and constraint methods, explicit provenance, resource outcomes, and declarative KB loading.
What happens when ESLM cannot answer?The primary status remains UNKNOWN or UNPARSED. A separate grounding bundle may contain bounded, related KB evidence. That evidence is labeled answerSupported: false; it is context for a person or downstream model, not a disguised answer.
Which acceptance gates come next?The next gates cover broader English parsing, general multi-step planning, mature temporal and defeasible reasoning, scalable document retrieval, encyclopedic coverage, and externally reproduced end-to-end benchmark results.

The repository distinguishes software checks, authored fixtures, generated internal development suites, external development probes, fresh evaluations, annotation or solver tracks, and official tests. They answer different questions and must not be collapsed into one “ESLM accuracy.” A newly assembled report can also contain older receipts; its assembly timestamp is not proof that every benchmark ran again.

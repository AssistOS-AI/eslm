Executable Symbolic Language Model

A deterministic language system built from explicit symbolic capabilities and declarative knowledge

ESLM is an engineering program for language understanding in which the deployed system is inspectable from input to result. It does not hide facts, rules, task interpretation, or control flow inside opaque weights. It compiles natural-language input into symbolic structures, builds an explicit task frame, selects declared capabilities, executes a bounded plan over trusted runtime code and declarative knowledge packages, and returns the answer together with provenance, unresolved subgoals, and operational evidence.

The boundary that defines the project

The project separates two very different activities. During training and knowledge construction, a coding agent may read a frozen, training-visible packet and propose normalized terms, assertions, rules, contexts, mappings, and provenance records. Those proposals are untrusted data. They pass schema checks, deterministic compilation, package audits, regression tests, evaluation, and an explicit promotion decision. During deployment, none of that agent machinery exists in the reasoning path. Runtime code is ordinary dependency-free Node.js; knowledge is JSON and JSONL; network access, agent calls, dynamic knowledge imports, source-string execution, and eval are forbidden.

This separation is not merely a packaging preference. It makes every promoted claim answerable: which source supported it, which compiler accepted it, which package version supplied it, which inference method used it, which rule produced a derived fact, and why the system abstained when a capability or premise was absent. A KB payload cannot silently gain executable authority, because it is never loaded as JavaScript.

What “language model” means here

The term denotes a system that interprets and constructs language by executing a model of linguistic forms, discourse state, world assertions, task operators, reasoning methods, and realization choices. The initial implementation intentionally supports a controlled English route before broader language induction. That route is useful because it makes failures local: a result can distinguish unsupported wording from unresolved reference, absent knowledge, an unavailable inference method, a trust conflict, or a resource limit. Later statistical or induced components may rank alternatives, but they do not erase the symbolic contract or replace explicit verification.

The system is organized around reusable capabilities rather than benchmark labels. Retrieval, safe Horn deduction, induction, abduction, context handling, provenance traversal, planning, and realization are registered with preconditions and proof obligations. A benchmark case is converted into the same task representation as an interactive request. This prevents a benchmark adapter from becoming an unreviewed second runtime and makes comparison evidence meaningful.

Core, knowledge, and methods

The generic core owns representations and mechanisms that should remain valid across domains: normalization, controlled-language parsing, entity and variable handling, task frames, the capability registry, plan construction, safe rule execution, provenance, trust policies, budgets, caches, and structured result production. A knowledge base owns domain content: terms, lexemes, assertions, rules that are justified for that KB, contexts, source records, mappings, and optional source-specific indexes. A method declares when and how a capability can be used. Keeping these responsibilities separate is the main defense against turning one solved benchmark into hidden generic behavior.

The boundary is tested. A proposed generic rule that mentions a corpus label, a benchmark answer, or a domain constant fails review. A KB record without provenance fails validation. An unsafe rule whose conclusion introduces an unbound variable fails compilation. A package whose shard hash differs from its manifest fails opening. A query that cannot be completed yields a structured gap rather than a fabricated answer.

Review discipline

A useful review starts with the relevant DS files and then follows their contracts into source, package data, tests, and measured reports. It does not infer capability from a demonstration alone. A successful “Define dog” query establishes one routed WordNet behavior under a particular package and memory mode; it does not establish general lexical understanding. A passing controlled-English inference establishes the tested construction and inference path; it does not establish unrestricted English. Claims remain attached to their source split, package version, runtime version, budget, and scoring protocol.

The documentation deliberately explains the system from several viewpoints instead of compressing it into slogans. Architecture pages describe ownership and execution. Language pages describe representation and interpretation. Knowledge pages describe data and trust. Training pages describe agent authority and artifact gates. Evaluation pages describe what evidence can and cannot justify. The DS files remain the complete contractual source whenever an implementation decision depends on exact wording.

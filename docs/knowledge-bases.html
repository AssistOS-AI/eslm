ESLM Documentation / Knowledge Bases

Selectable executable knowledge modules

A knowledge module is an independently versioned graph of senses, entities, facts, rules, aliases, and indexes loaded with --kb. The three modules currently present are small hand-authored regression fixtures. The source-derived queue is WordNet, ATOMIC, filtered ConceptNet, and bounded GeoNames; Wikidata is optional and thematic only.

Current evidence boundary

No current module contains public WordNet, ConceptNet, Wikidata, ATOMIC, DBpedia, GeoNames, or Wikipedia knowledge. The fixture counts below prove that loading, semantic deduplication, cross-module rule composition, and validation work. They do not measure factual coverage or knowledge learned from a realistic source.

Why the modules are not loaded automatically

A small application may need animal facts but no astronomy. A benchmark must often execute with exactly the model synthesized from its train split. Loading every available fact would increase memory, introduce irrelevant candidates, and make an experimental score difficult to interpret. ESLM therefore starts with no educational KB and accepts an explicit selection through --kb.

Entity IDs shared by two modules are merged only when their declared kinds agree. Identical facts and rules are deduplicated by semantic signature. Conflicting entity declarations fail model loading. The combined artifact is marked benchmarkComparable: false, so a result cannot silently masquerade as the clean bAbI run.

The individual source totals are 40 entity declarations and 68 direct facts. Loading all modules yields 36 entities and 62 direct facts because child-basic and space-geography intentionally agree on Earth, Sun, Moon, the Solar System, and six corresponding category/location facts. Rule closure then adds 54 supported consequences. This is more than the 30 consequences obtained by closing the modules separately: animal classifications can enter the living-being rules supplied by child-basic. That cross-module composition is useful, visible in provenance, and one reason selection must be explicit.

List, select, rebuild, and validate

node src/cli.mjs kb list
node src/cli.mjs kb show child-basic
node src/cli.mjs ask "Jhon is a man. Is Jhon going to die?" --kb child-basic
node src/cli.mjs --kb all
node src/cli.mjs kb build all
node src/cli.mjs kb validate all

kb list reports exact direct, derived, and executable fact counts plus tested examples. kb build compiles the declarative files in training/KBs/QUICK/source/ into domain directories under training/KBs/QUICK/model/. Each directory contains seven auditable ESM modules. kb validate checks imports, forbidden capabilities, referential integrity, rule shape, and index equality.

From fixtures to source-derived profiles

The first public module will be oewn-2025/core-senses. Unlike the fixture graphs, it must preserve lexical sense identity, definitions, relation type, source attribution, and corpus statistics. ATOMIC will then add participant-bound event hypotheses, ConceptNet will add relation-specific commonsense, and GeoNames will add bounded geography. Any later Wikidata pack must be justified by a concrete domain experiment. The real knowledge sources page defines these stages in detail.

Evidence and experimental use

These three KBs were generated by the coding agent for this repository, not learned from bAbI and not copied from a public benchmark. Every fact has generated-kb: provenance and every module declares benchmarkEligible: false. They are useful for development, demonstrations, modularity experiments, and testing deeper rule composition. They are not evidence of broad world knowledge and must not be mixed into a public benchmark score unless the experimental condition names the modules and is reported separately.

Canonical records, deterministic packages, catalogs, routing, and trust

A knowledge base is data with a logical interpretation, not a directory of generated programs. Source evidence is normalized into canonical records. A trusted compiler validates cross-record invariants and emits content-addressed JSON shards plus a manifest. The runtime opens only packages registered in its catalog and reads only allowlisted paths whose hashes match the manifest.

The canonical record model

The record vocabulary includes source and provenance records; contexts; terms and lexemes; assertions; rules; mappings; and, as later capabilities require them, events, temporal relations, modalities, trust statements, defaults, exceptions, and method-support metadata. Each record has a stable identifier and a declared type. References use identifiers rather than embedding executable expressions. Canonical JSONL is convenient for streaming, review, diffs, and deterministic recompilation.

Provenance is part of meaning. An assertion identifies the provenance records supporting it. Provenance points to a frozen source, document location, extraction method, and confidence or trust information where available. A rule identifies why it is licensed and its scope. A record without required provenance is invalid even if its content happens to be true.

Compilation is a security and reproducibility boundary

Validation occurs at several levels. Record validation rejects an unknown type or malformed field. Graph validation rejects dangling identifiers and missing provenance. Logical validation rejects unsafe rules and unsupported operator shapes. Package validation rejects paths outside the package, duplicate shard roles, incorrect byte counts or checksums, and incompatible schema or compiler versions. A build report records counts and source hashes but cannot substitute for these checks.

Compilation does not “improve” source claims by inventing missing facts. It normalizes, indexes, and partitions accepted records. Source-specific adapters may preserve compact formats when converting a huge resource into the full canonical form would add unacceptable size or latency, but those formats remain declarative and their semantics are documented and tested.

The small quick package follows the complete canonical path and is used for deterministic smoke tests. Its canonical data includes provenance, terms, lexemes, facts, a context, and safe rules. The current Open English WordNet and ATOMIC packages are rebuilt from cached immutable archives into provider-specific JSON shards. Their old generated .mjs payloads no longer participate in the product.

Catalogs and composition

A catalog entry binds a logical KB identifier and version to a package manifest and declares its provider and loading policy. Selection is explicit through CLI options or runtime configuration. Composing packages does not merge their source authority: provenance and context stay attached to every contribution, and conflicts are handled by declared trust and context policies. Package order must not silently decide truth.

The base core has no domain assertions. Selecting quick supplies its small development vocabulary. Selecting oewn-2025 supplies lexical senses, glosses, and relations. Selecting atomic-2020 supplies defeasible event-centered commonsense tuples. These resources answer different kinds of questions and must not be presented as one homogeneous truth store.

Query-directed loading

The loader derives conservative routing keys from the normalized query. A WordNet definition request routes by lemma and then loads the synset shards named by the lemma index. An ATOMIC question routes by normalized event key. Generic canonical packages may route by entity, predicate, lexical form, or declared index. Each selected shard is checked against the manifest before decoding.

The cache bounds resident shard data according to the runtime memory plan. It records hits, misses, loads, evictions, and bytes. Eager mode remains useful for small packages and controlled measurements; lazy mode is the normal path for large sources. Tests compare eager and lazy semantic answers on randomized samples so performance work cannot silently change meaning.

What a reviewer verifies

For an extraction change, compare frozen source hash, split visibility, assignment packet, candidate records, rejected evidence, and extraction coverage. For a compiler change, compile the same records twice and compare bytes and manifests, then exercise malformed paths, hashes, references, and rules. For a runtime change, verify catalog allowlisting, eager/lazy equivalence, cache budgets, provenance in answers, and deliberate gaps for absent content.

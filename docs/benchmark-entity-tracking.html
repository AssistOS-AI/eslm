Entity Tracking: executing container-state changes

Entity Tracking asks which objects remain in a queried container after a sequence of additions, removals, and moves. It tests persistent identity and state updates rather than factual recall.

Representation and execution

The reviewed adapter projects each bounded story into allowlisted operations. The generic state-transition method applies those operations in order and records the resulting container contents. This representation lets tests rename every object and container, insert irrelevant operations, reverse a movement, or query a different container without adding source vocabulary to the state engine.

Current ESLM protocol

The latest development probe executes 100 deterministically selected cases from a 20,020-row development artifact. Selection cycles across different operation counts so the sample is not only the shortest stories. The scorer compares the final unordered contents required by the masked span. Every required entity must appear and no extra entity may be returned.

The score shown on the home page therefore means that the stated number of selected structured cases produced the exact final set. It does not mean that every available development row ran, that other splits ran, or that unrestricted event prose can be converted into operations. Those are separate coverage questions. The current numerator, denominator, and tested-versus-available counts are read from the replaceable public-probe JSON rather than copied into this stable protocol page.

Failure interpretation

A wrong set indicates an operation, ordering, binding, or output-projection error. UNPARSED would indicate that the adapter could not construct the declared operation sequence. UNKNOWN would indicate that the sequence was understood but lacked the state needed for a determinate answer. The published sample is development evidence and must be accompanied by nonce objects, changed operation order, removal controls, and queries whose correct result is empty.

ESLM Documentation / Language / Basic questions and task context

Natural basic questions and query-local KB context

ESLM now creates a fast, bounded knowledge context for every eligible English request. The context recognizes ordinary standalone or embedded questions, asks a finite set of generic follow-up questions internally, and retrieves relevant records from the selected KBs. It helps later planning and wording while remaining explicitly separate from proof.

What changed

The direct factoid frontend now understands natural copular definitions. What is a cat? is represented as a definition request for cat and reaches the same provider route as What does cat mean?. This is a generic structural rule: nonce-renamed requests such as What is a zoral? behave the same way, while progressive and arithmetic neighbors such as What is Alice doing? and What is 36 plus 12? are not reclassified as definitions.

A new task-context-coordinator runs after the English-likelihood gate and before ordinary direct execution. It detects explicit questions and questions embedded in a larger instruction, resolves only safe local references, identifies request topics, creates a prioritized self-question plan, and consults the already selected KB scope. Its public extension is eslm-task-knowledge-context-v1.

The context branch cannot choose what the English means and cannot authorize a premise. It supplies a bounded topic and evidence frontier to later processing. The direct branch remains responsible for exact parsing, methods, witnesses, and strict answers. Both meet again only at validated result construction.

The taxonomy describes what information is requested, not one fixed wording. A provider may support only some families. Recognition without a matching KB record creates a typed gap rather than a fabricated answer.

How the default strategy creates context

strategy:context:question-facet-expansion@1 is the mandatory baseline. Explicit requested families receive highest priority. For each bounded topic it then considers definition, identity, taxonomy, properties, purpose, capabilities, requirements, method, location, effects, risks, limitations, provenance, conflict, relations, examples, history, alternatives, and stakeholders. It deduplicates topic-family pairs and records omitted work instead of pretending every possible facet ran.

Natural coordinated subjects are split only through a bounded nominal construction. For example, Where do zorals and velins live? remains one location question but creates independent zorals/location and velins/location information needs. Providers can annotate records with generic question-family support, allowing requested location relations to outrank unrelated definitions or taxonomy edges. The annotation changes relevance only; it cannot grant premise or answer authority.

Name lookup has an additional semantic gate. The focus receipt preserves the original Unicode surface and distinguishes a proper-name-shaped subject from a common, determiner-led, or possessed nominal. GeoNames may use an accent-folded index to find a bounded candidate set, but a record enters task context only when the focus is a proper name and its Unicode-preserving surface matches the record's canonical name. Consequently, a common noun such as cat cannot surface the place Çat merely because both share one folded index key. Exact typed exclusions and Unicode mismatches are counted in the source receipt.

The initial bounds are 16 question surfaces, eight topics, and 64 self-questions. The selected work profile imposes stricter limits on focus terms, provider sources, lookups, values, candidate entries, returned entries, and output bytes. Each consulted source returns a completion or truncation receipt. A complete empty search is therefore distinct from an incomplete search that happened to return nothing.

Precise answer versus useful partial context

OutcomeVisible behavior and authority
Precise route succeedsThe original SOLVED or DEFEASIBLE answer remains unchanged; machine clients may inspect the context extension. The existing method and witness own the answer.
Precise route lacks the requested bridgeknowledge-context-fallback may return PARTIAL, state that the full answer was not established, cite a few relevant source claims, and name the remaining gap. Citations authorize only what each source states; values stay empty.
Ambiguity, inconsistency, non-English rejection, or resource refusalNo contextual fallback is used to conceal the blocking condition. The existing gate retains authority.

The fallback ledger records the exact pre-context status as originalStatus. Thus a local route may truthfully record that no Language Agent proposal was needed at UNKNOWN, then publish a final PARTIAL contextual artifact. Validation compares those two explicit phases instead of requiring their statuses to be identical.

For progressive and do-support location questions, the analyzer keeps the complete possessive nominal as the topic and treats living or live as the relation cue. It therefore retrieves context for his cat, not for the accidental phrase his cat living. This improves focus only; ownership resolution and any defeasible carrier answer still require their separate language and witness contracts.

Focus roles also protect source boundaries. When a recognized family supplies typed focus, an entity subject or relation cue is not submitted to an event-only neighborhood merely because an event corpus has an exact one-token key with the same spelling. Only a subject typed as an event is eligible there; ordinary content terms remain available for open questions that have no typed family focus. Exact source lookup therefore cannot erase the entity-versus-event distinction.

For example, if WordNet defines both cat and blue but the KB does not establish that a cat is blue, ESLM may show those definitions only after saying it cannot establish the requested property. It may not infer the property from lexical relevance. Realized source claims enter top-level provenance and usedKbVersions; unused context remains only in the context packet.

A constituent match is also insufficient. A fact about Penguin may remain useful internal context for an unknown surface such as fake Penguin, but it cannot be realized as a claim about that compound entity. Parser-rejected nominal surfaces receive the same protection.

Machine contract and review checklist

The extension exposes question analysis, self-question plan, focus candidates, exact selected and consulted KB versions, ranked entries, per-source receipts, limits, completeness, strategy selection, and an optional realization ledger. It always declares answerSupported: false, premiseAuthority: none, and interpretationAuthority: none.

Reviewers should verify that a renamed nonce topic follows the same route, a common-noun/proper-name Unicode collision is rejected while the exact Unicode name remains retrievable, provider order cannot change the context, strict answers do not gain distracting prose, every cited fallback sentence maps to an exact context record, and likely non-English requests consult no KB. The authoritative contract is DS035.

ESLM Documentation / Concepts

ESLM concepts and vocabulary

This page defines the objects named throughout the documentation. No knowledge of symbolic AI is assumed. The only prerequisite is understanding that a program can transform structured input into structured output.

The central idea

A conventional search system finds text that looks relevant. ESLM instead tries to identify what relation a question asks for, resolve the named entities, execute stored facts and rules, and then generate a supported answer. Its model is a set of Node.js modules rather than a matrix of neural weights.

Core and generated model

The core is ordinary source code under src/. It defines how to tokenize, parse, index, unify rules, trace evidence, and form English answers. The generated model is the promoted module graph under training/model/. It defines which entities, facts, rules, aliases, and accepted lexical variants exist for one trained artifact.

Changing the training corpus should primarily change generated modules. Changing the semantics of unification or the meaning of UNKNOWN changes the core and requires a product specification change.

Entity, alias, predicate, and fact

An entity is something with stable identity, such as mars, penguin, or solar-system. “Solar System” and “the Solar System” are aliases for the same entity. Stable identity lets different sentences and rules refer to one object without comparing prose.

A predicate names a relation or attribute, such as owns, located_in, or color. A fact binds a subject, predicate, and object or scalar value:

{
  "id": "space:f15",
  "subject": "mars",
  "predicate": "located_in",
  "object": "solar-system",
  "provenance": ["generated-kb:space:f15"]
}

The fact says what the model asserts and which training record supports that assertion. It does not store a prewritten answer.

Construction and query

A construction is a supported English form with typed slots. where is ENTITY requests the location predicate and leaves its object slot open. who owns ENTITY fixes the owned object and leaves the owner slot open.

A query is the semantic object produced after a construction is matched. With the space module loaded, the query for “Where is Mars?” is approximately:

{
  "intent": "location",
  "subject": "mars",
  "predicate": "located_in",
  "target": "object"
}

The query contains no sentence-generation instruction. It says which evidence to retrieve and which field becomes the semantic answer.

Index and posting list

An index maps a key to the facts that contain it. A posting list is the list of fact positions for one key. The subject posting for mars contains its category, location, and color facts. The predicate posting for located_in contains all direct location facts. Intersecting them finds Mars's location without scanning unrelated colors or continental relations.

Rule, binding, and derived fact

A rule has premise patterns and a conclusion pattern. Variables start with ?. A binding assigns concrete IDs to those variables consistently across all premises. When the child knowledge base sees the session fact (jhon, is_a, man), successive bindings produce human, living-being, and eventual-death facts. The final proof has depth three.

Derived does not mean guessed. The result records the exact rule and direct facts used. Read Reasoning Trace for the complete execution.

Provenance and proof support

Provenance identifies where an encoded claim originated. Proof support identifies which executable facts and rules produced a conclusion. A generated direct answer may cite generated-kb:space:f15. A Task 15 answer cites a temporary universal rule and an episode classification. A cross-module consequence may cite an animal classification plus a living-being rule from child-basic.

Result statuses

StatusMeaningExample
ANSWEREDA semantic value has direct or deductive support.“Is Mars a planet?” with the space KB.
INDUCTIVEA configured observed pattern meets support and coverage thresholds.“Is Dana likely to fly?” in the reasoning fixture.
ABDUCTIVEGrounded rules yield ranked possible explanations, not proven causes.“What could explain why the lawn is wet?” in the reasoning fixture.
UNKNOWNThe query is supported, but the active model lacks proof.“Can Penguin fly?” with the animal KB.
UNSUPPORTEDNo construction or executor represents the request.“Write a poem.”
AMBIGUOUSSeveral supported entity or construction analyses remain.Two entities share an unresolved mention.
NEEDS_CLARIFICATIONA user choice could select one analysis.Planned end-to-end clarification flow.

Training packet, candidate, and promotion

A training packet is a validated, hashed view of agent-visible evidence. A candidate is a generated module graph in an isolated directory. Promotion is the reviewed replacement of the default model after safety checks, semantic validation, and evaluation. The coding agent may create a candidate; it does not promote its own output.

Experiment model and knowledge module

The promoted experiment model is the default artifact selected for a public run. An optional knowledge module is a separate generated graph loaded by ID with --kb. Keeping them separate allows a clean benchmark condition, smaller active indexes, and domain-specific demonstrations. A merged model records every selected KB and is not directly comparable with the default run.

# DS005 Generated Code Model, Compression, and Indexes

## Core Content

### Model as code

The promoted artifact is a static ESM module graph rooted at `training/model/manifest.mjs`. It exports frozen entities, facts, rules, lexicon/constructions, and indexes. The manifest declares `eslm-code-model-v1`, model identity, generation time, source digest, evidence regime, and eventually an exact inventory of shards.

Code is used because a coding agent can reorganize evidence into specialized data structures and bounded helpers that Node loads directly. The scientific comparison is not “JavaScript versus weights” in the abstract; it is explicit program synthesis and executable compression versus learned parameterization under controlled evidence.

### Identity and entities

Entity ids are stable across local rebuilds whenever identity is unchanged. Each entity has English display names, aliases, and a semantic kind. Future schemas add attributes, temporal existence, source-specific mentions, and equivalence confidence without collapsing source mentions prematurely.

Aliases normalize to at most one promoted entity in v1. If the corpus contains homonyms, the model must represent mention candidates and disambiguation context in a future format rather than violate uniqueness. Sequential numeric ids are acceptable for large models only when an intern dictionary and stable mapping digest are frozen.

The v1 uniqueness rule cannot represent WordNet polysemy. Source-derived providers therefore use `eslm-public-kb-v1`: a lemma maps to multiple synset IDs and source identity remains intact. This format currently supports source-specific lexical and event query contracts without forcing those records through the globally unique v1 entity graph.

### Facts and epistemic scope

Facts use subject, canonical predicate, and exactly one entity object or scalar value. Every fact has a stable id and nonempty source provenance. Time, modality, negation, uncertainty, source belief, and discourse scope are explicit fields when present; encoding them in invented predicate names would destroy reasoning semantics.

Large-corpus claims additionally carry world, valid-time, spatial, domain, perspective, modality, and polarity scope as required by DS019. Scope participates in identity and conflict checks; matching values under different fictional worlds or times are not duplicates.

Conflicting facts are retained with their sources and epistemic status. A reducer may cluster duplicates but cannot select a winner silently. Query policy can prefer recency, authority, or a named source only when the contract declares that policy.

### Rules

Rules are bounded Datalog-like triple patterns with variables. The v1 reasoner supports positive conjunction and one triple conclusion. Rules cannot create anonymous entities, call code, mutate external state, or rely on negation-as-failure. Provenance combines rule source and supporting facts.

Induced rules include confidence, support count, and counterexamples when the format is extended. A rule that holds only for one entity belongs as a fact unless a semantic source explicitly states the generalization.

### Index families

Small models include direct posting lists by subject, predicate, and object/value plus normalized alias maps. Larger models add:

- dictionary-interned entity and predicate ids;
- sorted integer postings and intersections;
- predicate or domain shards;
- prefix tries or minimal automata for aliases and constructions;
- event indexes by participant, type, and time;
- rule indexes by head predicate and premise predicates;
- narrative schema transition tables;
- source-to-claim reverse indexes for audit and invalidation;
- optional cache tables for verified high-frequency derivations.

Every acceleration index is derived from canonical modules and validated against them. Indexes do not become a second source of truth. A stale posting is a promotion failure.

V1 index creation now appends instead of copying a posting list on every insertion. Large profiles still require sorted integer postings, streaming validation, relation-and-scope shards, and static manifest metadata that supports planning without importing every claim.

### Executable compression

Compression groups semantically identical representations, interns repeated strings, factors common constructions, stores facts in column-compatible arrays, and reuses rule and realization schemas. Generated source remains reviewable; minification is not the objective.

The compression report contains source bytes, generated bytes, canonical claim count, retained source references, module count, import latency, median/p95 query latency, and semantic reconstruction hash. A smaller module with missing qualifications is data loss, not a better model.

Minimum Description Length guides tradeoffs. Adding a reusable rule may reduce repeated fact encoding, but rule complexity and errors count against it. A catch-all function that contains corpus prose in branches has high effective model cost and poor generalization even if its byte count is low.

### Module safety and determinism

All imports are static and local. Import has no I/O or time-dependent behavior. Values are frozen where practical. Pure helper functions are bounded and cannot access ambient authority. Source literals are safely escaped; corpus text cannot close a string and introduce syntax.

Validation scans for forbidden capabilities, imports the model, checks format, unique ids, references, fact shape, provenance, rule shape, and index consistency. An isolated candidate is reviewed before replacing the promoted module graph.

### Upgrade path

The initial six modules may split into `events`, `discourse`, `narrative`, `realization`, and fact shards. The manifest stays the only entry point. Runtime loaders select only declared format versions and known module keys. Format evolution uses migrations and retains old report readers.

`eslm-code-model-v1` remains the promoted core and QUICK graph format. Open English WordNet and ATOMIC use generated static shards plus `eslm-public-kb-v1` manifests. Their first complete builds prove source compilation and runtime semantics, but manifests currently import and merge all shards eagerly; dividing data into files alone does not satisfy the DS019 query-directed scale target.

### Promoted artifact and optional KB artifacts

The promoted bAbI Task 15 artifact is an episodic compiler. Its persistent entity, fact, and rule arrays are empty because each story defines a distinct world. Its generated knowledge is three construction declarations, four plural-to-singular mappings, and bounded reasoning policy. The prepared train digest and `babi-task-15-train-only` evidence regime identify that artifact.

Each optional KB is a complete `eslm-code-model-v1` graph under `training/KBs/QUICK/model/ID/`. Its manifest additionally declares title, semantic version, generated-by method, source digest, scope, examples, and `benchmarkEligible: false`. Sources are compiled by deterministic Node code from `training/KBs/QUICK/source/ID.json`.

## Decisions & Questions

### Q1. Why not store the model only as JSON?

Response: JSON would support the simplest tables, but generated ESM also permits static composition, compact typed arrays, pure specialized lookup helpers, and direct module sharding. Safety restrictions keep the executable advantage bounded.

### Q2. Is generated source itself trusted knowledge?

Response: No. Canonical facts and rules remain claims tied to source provenance. Generation transforms representation but does not increase epistemic authority.

### Q3. What determines module boundaries?

Response: Semantic cohesion, index locality, independent validation, and incremental rebuild behavior. Arbitrary equal-sized shards are a fallback only for scale.

### Q4. Which fact count is authoritative for a modular model?

Response: No single unlabeled count is sufficient. Reports provide source declarations, unique persistent direct facts after merge, session facts for the current episode, and executable facts after bounded closure. Rules are counted separately. This prevents training examples, stored claims, and derived consequences from being conflated.

### Question #5: Is a directory of many ESM files automatically scalable?

Response: No. Scale requires compact values, selective imports, query planning, streaming validation, and bounded execution. Sharding full object arrays without those properties only relocates the same cost.

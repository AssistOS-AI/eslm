ESLM Documentation / Reference / CLI operations

One authority-aware interface across question, package, training, benchmark, and research operations

The CLI is the operator and implementation-reference plane for the same logical processing graph. All question modes construct the same runtime and return the same semantic protocol. Administrative commands build or validate declarative artifacts; they do not introduce a second reasoning path. Command blocks deliberately retain executable entry-point and fixture paths because this page is their reference owner.

For the processing nodes behind these commands, use the logical architecture. This page keeps only operator-visible configuration, command syntax, structured outputs, and failure behavior.

Ask one question

node src/cli.mjs ask "Can Penguin swim?" --kb quick
node src/cli.mjs ask "Can Penguin fly?" --kb quick
node src/cli.mjs ask "Define dog" --kb oewn-2025
node src/cli.mjs ask "Why might apologize?" --kb atomic-2020
node src/cli.mjs ask "QUESTION" --external-language-agent
node src/cli.mjs ask "QUESTION" --no-external-language-agent

The output is JSON. Read status and answer first. Then inspect the stage-dependent fields that are present: values, input, query, taskFrame, plan, provenance, and reasoning can be absent after an early UNPARSED. Every text result still reports selectedKbVersions, consultedKbVersions, contributor-only usedKbVersions, unresolvedSubgoals, and model.memory. If grounding is present, it is a separate related-evidence search and never part of the answer. The WordNet and ATOMIC examples exercise source-specific declarative providers; the quick examples exercise the canonical generic compiler and loader.

The local runtime is English-only. A bounded assessment reports likely-english, likely-non-english, or indeterminate; a likely-non-English refusal uses route english-language-gate-rejected and does not attempt translation, KB lookup, planning, or grounding. Continuing input uses direct parsing plus deterministic request and interpretation recovery. Explicit request force can preempt an accidental assertion parse while restoring the incoming session snapshot. A changed local interpretation also starts from that snapshot and remains query-local for every eligible direct status.

The general CLI uses the fully local symbolic path by default. --external-language-agent or interactive /normalize on explicitly opts into the disclosed Language Agent proposal wrapper; --no-external-language-agent or /normalize off explicitly retains the local default. In the assisted profile, a likely-non-English refusal may request translation directly. English or indeterminate input can request simplification only after local recovery remains UNPARSED. One episode permits at most three proposals. A later proposal may receive bounded surface-validation errors or narrow parser feedback; it never receives a symbolic answer, KB result, proof trace, expected value, or benchmark label. Assisted results expose the exact strategy identity and stage, proposalRole: untrusted-language-form-candidate, answerAuthority: none, operation, adapter, model, proposal and invocation counts, cache state, validation, and reparse status.

Host validation is deliberately restrictive. English simplification needs one-to-one protected occurrence coverage plus equality of reviewed open-class and function-word multisets. Translation must produce likely English and survive direct reparse, but those checks cannot establish open-class source-to-target equivalence. Model-declared alignments are not independent proof; without a separately reviewed preservation profile, translation returns UNVERIFIED_NORMALIZATION. The adapter caps each process output stream at 2 MiB, the response JSON at 1 MiB, and a cache entry at 4 MiB. Timeout or output overflow escalates from SIGTERM to SIGKILL after 250 ms and cannot wait forever for child settlement.

Every question first emits a restrained bounded-processing activity line with the effective work profile and the decisive interpretation, reparse, loaded-source, and context-lookup caps. Interactive presentation then gives every completed result the same two-part shape. A muted gray Thinking · symbolic processing block explains the route, status, method, evidence count, and authority boundary, followed when applicable by query-local KB context and the resource budget; grounded symbolic generation additionally names its five-node construction circuit and selected sentence and assembly strategies. A verified defeasible answer also shows its confidence grade and explicit assumption. A local UNPARSED may recommend explicit Language Agent opt-in, but that text does not invoke an external process. This is an operational stage-and-receipt summary, not private chain-of-thought. A clean Answer block follows. When the machine answer is a short raw value such as a direction or identifier, the interactive renderer turns it into a short English sentence for readability; the JSON result retains the original typed answer and values.

External Language Agent activity is a separate event, not the interactive symbolic-processing summary. Immediately before each real subprocess call the interface emits exactly one additional attempt-aware line naming translation or simplification, the proposal slot, Codex adapter, and enforceable per-call timeout. One-shot and batch commands send all activity to standard error, so JSON and JSONL standard output remain valid; a cache hit emits no live-invocation line. /normalize shows the proposal and timeout limits. An accepted simplification keeps the original, transformed English, external activity accounting, and final symbolic result distinct. A skipped receipt is explained as “external assistance was not needed”; the UI never exposes “unattempted normalization” as a user error. A rejected translation keeps the original, proposed English, and host-owned preservation gap visible. Fluency never overrides failed validation.

An unexpected request-local parser, provider, context, normalization, construction, or result-schema exception is contained by the interactive loop. The failing request does not replace the prior result or session context, the UI reports which safety boundary rejected it in ordinary language, and the prompt remains open. Local work is bounded by counted resources; external subprocesses additionally have a timer and termination escalation.

Work and trusted-strategy inspection

node src/cli.mjs ask "QUESTION" --work-profile deep

# Inventory view only
node src/cli.mjs ask "QUESTION" --strategy-preset retrieval

# Exact execution allowlist; quote semicolon-separated assignments in a shell
node src/cli.mjs ask "QUESTION" --strategy-select \
  'runtime.evidence.assess=strategy:retrieval:focus-term-cooccurrence@1,strategy:retrieval:typed-answer-bridge@1'

# Interactive
/work
/work exhaustive-bounded
/strategies
/strategies reasoning
/strategy runtime.reason.execute=strategy:core:safe-horn-deduction@1
/strategy clear

--work-profile selects exact bounded heuristic, Horn, provider, and grounding limits. Interactive /work prints those limits and /work PROFILE rebuilds the runtime without changing selected KBs or session facts. The four profiles are quick, balanced, deep, and exhaustive-bounded; the final name denotes the largest current finite profile rather than an unbounded corpus or proof search.

--strategy-preset accepts all, language, retrieval, reasoning, or construction. It changes only the inventory view. /strategies reports catalog, execution-enabled, coordinated, instrumented-local, and planned totals, stage counts, and the selection digest; /strategies PRESET filters that report. Neither form enables or disables an executor. In this inventory, “execution-enabled” means admitted by an available exact policy gate, not “observed in the last request”; receipts supply actual execution evidence. A local owner marked catalogued-not-policy-gated may still run in the normal pipeline while remaining unavailable to /strategy.

--strategy-select 'STAGE=ID[,ID];STAGE=ID' is the exact execution control. The value is quoted in shell examples because semicolons separate stage assignments. Interactive /strategy STAGE=IDS applies the same closed syntax; /strategy clear returns to the default built-in selection. Validation rejects unknown or wrong-stage identities, duplicate stage assignments, empty arrays, planned strategies, and removal of the mandatory direct parser or function-word exclusion strategy. An invalid interactive selection leaves the current engine unchanged.

The selectable stages are runtime.language.interpret, runtime.request.plan, runtime.knowledge.focus, runtime.evidence.assess, runtime.reason.execute, and runtime.result.construct. The 24 language families execute through the sealed shared registry and coordinator. The other selectable stages honor the exact gate inside their current instrumented-local owner. Retrieval-frontier execution, failure grounding, method planning, and verification are catalog-visible but non-selectable until they genuinely cross the common coordinator. See Processing-node strategies for identities, receipts, and the remaining integration gates.

Recovery when the primary answer is unavailable

The current runtime can append a bounded grounding bundle after UNPARSED, UNKNOWN, AMBIGUOUS, MISSING_KNOWLEDGE, NO_APPLICABLE_METHOD, PARTIAL, UNDERDETERMINED, INCONSISTENT_CONTEXT, or UNSUPPORTED_OUTPUT. It searches the session, loaded canonical model, and selected providers that implement the grounding interface. The primary status, answer, values, provenance, and used-KB accounting remain unchanged. answerSupported is always false.

The current runtime does not run this fallback after RESOURCE_LIMIT. Starting more retrieval after an exhausted primary budget would hide the resource failure and may amplify an adversarial request. A future product may do so only with a separate budget reserved before primary execution and separately reported.

Interactive mode prints a distinct “Related KB evidence — not an answer” block. Batch and one-shot modes keep the bundle as structured JSON. /trace reports the answer premises first and grounding receipts separately. A downstream language model may consume the visible question plus the bundle only in a separately declared assisted-generation pipeline; that model is not the Language Agent normalizer, and its prose is not retroactive symbolic proof. The complete field guide, examples, receipt semantics, and failure modes are in Grounded failure and related evidence.

Interactive and batch operation

Running node src/cli.mjs opens a session. Statements can extend only that session’s context, and later questions can refer to those entities and facts. Runtime commands expose selected KBs and memory state. The session does not alter canonical records or compiled packages. External language proposals start enabled in the general CLI and are disclosed at startup. /normalize shows the state, model, and cache policy; /normalize on and /normalize off rebuild the operator wrapper without changing session facts or selected KBs. Pressing Tab completes slash commands, declared normalization and memory values, and available KB identifiers for /load and /unload. Completion only proposes text: it does not execute the command or alter ordinary-language input.

The current session command is deliberately coarse: /clear discards the entire temporary overlay. Fine-grained fact listing/retraction and a clarification dialogue are not implemented yet; ambiguity is returned as AMBIGUOUS for reformulation. Episode updates are atomic: if one statement is unsupported, tentative changes from that input are rolled back. Resource gates run before public-provider routing and return RESOURCE_LIMIT rather than allowing an oversized input or context to reach inference.

node src/cli.mjs run --input tests/fixtures/questions.txt --output /tmp/eslm-answers.jsonl

Batch mode reads input records and writes one result object per request. It is suitable for pipeline integration because answer text, semantic values, status, and evidence remain separately machine-readable. A failed case is written as a result rather than dropped from the stream. Each record has independent route accounting. The default local profile makes no external calls; an explicitly selected assisted profile records cache hits, live calls, rejected proposals, and accepted simplifications.

Authored and generated internal benchmarks

# Both reports, kept separate
npm run benchmark

# One report at a time
npm run benchmark:authored
npm run benchmark:generated

# Direct generated-suite replay and an explicit alternate sample
node src/cli.mjs benchmark generated --publish
node src/cli.mjs benchmark generated --cases 1200 \
  --seed eslm-generated-heuristic-development-v1 --publish

The default package command sequences two different internal measurements. The authored route runs the unchanged five-case fixture and publishes latest-benchmark.json plus its HTML view. The generated route defaults to 1,200 deterministic heuristic-language cases and publishes latest-generated-heuristic-benchmark.json plus its own HTML view. Both declare benchmarkComparable: false; the command never adds their scores together and never invokes the public adapter portfolio.

benchmark generated validates a finite --cases value and accepts a reproducible --seed. Each generated episode has a typed structural oracle derived before execution, nonce content vocabulary, a declared domain, technique, target family, and metamorphic relation. The runner disables the Language Agent and grounding and calls the actual local heuristic runtime. Its report freezes generator and suite digests, behavior and replay identity, work and strategy configuration, and aggregate outcomes by domain, technique, target family, complexity, route, status, confidence, and resource use. Earliest-failure clusters combine stage and target family while retaining their technique and domain distributions. A bounded set of representative failures supports manual diagnosis; unprinted failures remain in the cluster totals and denominator.

The top-level pass rate combines eight explicit software-contract levels: answer execution, semantic-query execution, candidate selection, query-local decomposition, request execution, request planning, safe abstention, and proposal-only preservation. Semantic-query rows require the complete relation-shaped query even when missing knowledge leaves UNKNOWN. Candidate-selection rows require the intended structural candidate to win but do not by themselves establish that complete query. Request planning validates every ordered obligation's intent, artifact kind, and format; request execution additionally validates construction and composite section shape. A complex-clause proposal may pass its family and safety checks while the final status remains UNPARSED. Read oracle level, route, and status beside the mixed rate.

Use the fixed seed to compare a change with its baseline, then run another seed to test whether the conclusion survives new names and combinations. Improve a strategy only when a repeated structural cluster and its meaning-changing controls support the same hypothesis. Public execution remains under benchmark probe, and fresh or official claims retain their separate DS010 protocols.

/examples [PAGE] [SEED] renders 24 cases from the exact default catalog used by /smoke. Its deterministic display order round-robins the eight heuristic oracle levels and the core capability groups, so page one already shows direct and repaired language, semantic-query execution, decomposition, request planning and construction, safe abstention, state and relation work, preference scoring, and both typed-task forms. Page one and page two remain different; each page states its 4,096-case display range, total page count, template identity, contract level, and metamorphic control. The stable shared default seed keeps both commands reproducible, while an explicit seed changes nonce surfaces without changing the obligations.

/smoke [COUNT] [SEED] executes the requested bounded mixture and defaults to all 4,096. The default contains 1,200 fresh cases from all 43 DS022 heuristic-development shapes plus 2,896 cases from 26 established core templates, for 69 visible template identities. Heuristic cases cover answer execution, semantic-query execution, candidate selection, query-local decomposition, request execution, request planning, proposal-only preservation, and safety abstention; core cases retain class and relation inference, state replacement, temporal and possession work, open-world controls, grammatical preference, Boolean entailment, and categorical logic. The command calls the complete local heuristic wrapper for language cases and the ordinary public engine boundary for direct, preference, and typed tasks, with Language Agent assistance and ordinary inability grounding disabled. It prints one actual execution per encountered template and every failure, then aggregates pass/fail beside contract level, observed route, and observed status. Every non-displayed case still contributes. A fresh offline generic-core plus QUICK runtime uses the balanced policy and default exact strategy set regardless of prior session, KB, memory, work, strategy, or normalization commands. These are project-owned regression cases, not public scores.

Every question mode validates its request and enters the same runtime. Human presentation and automated scoring are two consumers of one structured result.

Knowledge-package operations

node src/cli.mjs kb list
node src/cli.mjs kb records quick --limit 25
node src/cli.mjs kb records quick --match '*penguin*'
node src/cli.mjs kb search '*capital*' --kb quick,geonames-2026 --limit 20
node src/cli.mjs kb register /absolute/path/to/package/manifest.json
node src/cli.mjs kb unregister my-kb
node src/cli.mjs kb compile --input candidate/records.jsonl --output /tmp/my-kb-package \
  --id my-kb --version 0.1.0 --namespace my-kb
npm run kb:build
npm run kb:validate

kb list describes repository-managed and explicitly registered entries and their current package state. kb records returns a bounded prefix of the exact stored entries, while kb search accepts ordinary text or */? wildcards and may search one package, a comma-separated selection, or all. Each result says whether the result limit or byte budget stopped inspection and reports the package, shard, entry key, checksum-validated work, and bounded record or preview. Inspection is read-only and never interprets a record as executable code. kb compile repeats the host canonical validator, sorts accepted records, writes inert JSON shards, and emits a hashed manifest; compilation does not register or promote the result. Registration opens and validates the manifest before storing a relative catalog reference; unregistration removes only the catalog entry and never deletes package data. Building recompiles repository-managed KBs from canonical records or frozen source archives. Validation opens manifests, checks package invariants, and performs provider checks. Build commands are trusted host operations; they never execute source or candidate text.

The package inventory changes as sources pass their gates, so this page does not maintain a duplicate count or list. kb list is the executable inventory and kb show ID exposes one package's capabilities, source role, limitations, identity, and validation state without loading all shards. The knowledge-package chapter explains the stable package roles and safety boundary.

Training operations

node src/cli.mjs train prepare \
  --input tests/fixtures/training.jsonl \
  --namespace example-kb \
  --output /tmp/eslm-packet.json

node src/cli.mjs train candidate \
  --packet /tmp/eslm-packet.json \
  --output /tmp/eslm-manual-candidate

node src/cli.mjs train run \
  --packet /tmp/eslm-packet.json \
  --output /tmp/eslm-agent-workspace \
  --skill document-to-kb-builder \
  --dry-run

node src/cli.mjs train validate --model /tmp/my-kb-package

train prepare accepts only allowlisted training-visible record types and writes a frozen packet with a content hash and explicit target namespace. An omitted --output uses the operating-system temporary directory rather than recreating training/work/. Train-visible records are embedded as the assigned evidence container, while every source record still declares its media type, language, license, and content checksum. train candidate creates a manual candidate skeleton without launching an agent. train run creates an isolated workspace, computes the Stage A diagnostic baseline, and copies one named skill. Remove --dry-run only after inspecting the packet, assignment, workspace target, and selected skill. train validate opens a compiled package through the trusted host checks; the skill validator and kb compile are the preceding canonical-record gates. A successful agent exit, portable validation, compilation, or package validation does not promote its candidate. There is deliberately no train promote command until the reviewed version transition and publication policy are implemented.

Immutable downloads and extracted public data remain under ignored training/.cache paths. Dataset status reports the catalog entry, immutable archive, preparation manifest, split policy, and disk state for a named dataset. Corpus status distinguishes a cached source from a compiled package. Benchmark status reads the typed catalog and reports the exact local artifacts, access gates, source identity, adapter state, evaluation state, and next action for every current registration. This page deliberately does not copy that mutable inventory. A cached source has bytes available; it does not prove that its adapter ran, its score is current, or its license permits redistribution.

A memory option affects package planning and cache policy and is reported in the result; it does not claim a hard process limit. The CLI wrapper always reports its configured eslm-memory-plan-v1. With no public KB selected, the current automatic plan has an empty provider list and the fixed 96 MiB planning reserve. A library caller using EslmEngine directly instead sees an eager core snapshot with no soft target and zero reserve. In both cases an empty provider list means that no public-provider cache participated; it is not a zero-memory claim. The Language Agent normalization cache is different from a KB shard cache. Its entries are agent-derived text plus validation and process receipts, remain outside deployable packages, and retain assisted-route attribution even when no new subprocess runs.

benchmark catalog describes the current task families from typed registrations. Each entry carries queue stage, priority, capability contract, official source and paper, license or access state, cache identity, adapter state, evaluation state, and one explicit next action. The catalog can grow without changing this command contract. Catalog inclusion, source availability, and adapter validation do not claim that a case was executed or answered.

benchmark status inspects cache, source identity, adapter state, evaluation state, rights, and remaining action. Cache presence alone is never evidence of a current execution. Fresh receipts are classified as current, historical-stale, historical-unrecoverable, invalid, or unavailable; development-only caches may still report validated-frozen, cached-unvalidated, or absent. benchmark probe executes the configured public adapters and combines their live measurements with frozen research receipts in latest-public-benchmark-probes.json. The public probe command is deliberately direct-symbolic and rejects --external-language-agent; its normalization-candidate percentage counts direct UNPARSED results without invoking an agent. A separately frozen suite passed to benchmark run --external-language-agent produces the assisted track and records special-analysis cases, cache hits, external invocations, accepted and rejected normalizations, route-specific accuracy, and route counts.

A selected benchmark probe is diagnostic output and cannot overwrite the canonical portfolio. Publication requires exactly --benchmark all, the canonical 256 MiB advisory policy, and no custom KB override. Even then, the report says which rows executed now and which came from stored receipts. The receipt audit checks those stored checkpoints against current behavior dependencies; --require-current is the release gate and is expected to fail while historical-stale rows remain.

A row claimed as current also carries eslm-benchmark-strategy-configuration-v1. The snapshot binds requested and effective work profiles, exact allowlists, configured arbiter identities, and content-addressed catalog and configuration digests. Because one row contains many cases, actual coordinated activity is represented by per-stage aggregate receipt summaries with execution, complete, and incomplete counts plus a bounded unique-receipt digest/count ledger—not by one convenient case receipt. Adapter-local rows freeze their explicit local state. Stored rows without this snapshot remain historical or reporting-incomplete.

benchmark export creates a label-free prediction manifest. benchmark score-predictions requires exact protocol metadata, rejects duplicate and extra IDs, counts missing IDs in the denominator, and hashes the submitted predictions. benchmark import-results is only for aggregate values copied from an external primary source: it accepts the closed eslm-external-result-manifest-v1 schema, checks metric arithmetic, hashes the manifest, and always marks the result as a reference-only unverified aggregate. Imported percentages are never silently treated as locally comparable scores.

The full check runs unit and integration tests, deterministic KB validation, fixed-fixture evaluation, the separate authored and generated internal benchmark reports, specification-matrix generation, documentation checks, and training-package validation. Commands that publish a report replace the corresponding generated result artifact; reviewers should compare protocol, sample policy, suite or source hash, runtime identity, package versions, route policy, and budgets before comparing scores. A locally validated protected source such as EWoK receives a denominator and a precisely labeled diagnostic; a source that is still absent or invalid remains not-run, never zero.

Operational recovery and diagnostics

CLI syntax or invalid configuration exits nonzero and writes a concise diagnostic to standard error. A well-formed but unsolved language request normally returns a structured result, because inability to solve is part of model behavior rather than an operator error. Failure-time grounding may add related records, but it cannot change that failure into success. Package checksum failure, unsafe training data, or an invalid promotion artifact is an operator error and stops the command. An unavailable Language Agent model, authentication error, timeout, malformed JSON, rejected anchors, exhausted proposal limit, or failed reparse produces an attributed normalization failure and cannot turn partial output into a solved result. Interactive mode remains open after such a failure.

Metamorphic templates, generated examples, and regression smoke

Metamorphic testing checks a relation between executions when a useful oracle is easier to state for the transformation than for an isolated new sentence. ESLM uses deterministic templates and nonce values to prove that a mechanism follows semantic structure instead of memorizing names, source rows, answer positions, or familiar wording.

The test contract

A metamorphic template defines a source case x, a transformation T, and an expected relation between the results R(x) and R(T(x)). A meaning-preserving transformation requires the same semantic value and a correspondingly renamed trace. A meaning-changing transformation requires a predictable change, such as an inverse relation, a different queried container, or loss of a derivation. Both forms are necessary: preservation alone can hide a constant answer, while change tests alone can hide fragile parsing.

The template owns the expected relationship between two executions. It does not inject either answer into the runtime. The comparison checks values, statuses, and where required the reasoning trace.

Implemented template families

TransformationRequired relationship and defect it detects
Entity and predicate renamingReplace every content name with fresh nonce forms while preserving roles. The result and trace must change only through the same renaming. This detects rules tied to people, animals, places, objects, or benchmark vocabulary.
Alpha-renaming and statement reorderingRename variables and reorder independent premises. Logical conclusions must remain stable. This detects dependence on surface position or a particular variable spelling.
Distractor insertionAdd a well-formed but irrelevant fact or event. The answer must remain unchanged and the distractor must not appear as proof support. This detects uncontrolled lexical overlap.
Direction and argument reversalSwap relation endpoints or ask for the inverse direction. The output must become the declared inverse when one exists, rather than remain constant. This detects symmetric treatment of directional relations.
Premise removal or polarity changeRemove a required premise, negate it, or move it to an incompatible context. A former proof must disappear, become contradicted, or become unknown according to policy. This detects overgeneration.
State-operation permutationReorder dependent moves, change the moved entity, or query another container. The final state must change exactly as execution order requires. This detects bag-of-sentences state handling.
Chain extension and shorteningAdd a composable relation step or remove one. The composed relation or supported depth must change predictably. This detects fixed-hop and answer-frequency shortcuts.
Candidate-order swapSwap two preference or continuation candidates while preserving their content. The selected candidate identity must follow the content, not the first or second position.
Quantity and comparison substitutionReplace values with new ordered nonce quantities and update only the relations implied by that ordering. This detects memorized numbers and accidental lexical preferences.
Unsupported-form controlGenerate a request deliberately outside the declared grammar or capability set. The runtime must return the expected structured failure rather than fabricate an answer.

How /examples and /smoke use the corpus

The interactive regression corpus contains 4,096 deterministic generated cases in two accounted components: 1,200 fresh instantiations of all 43 heuristic-development shapes and 2,896 instantiations of the 26 established core templates. The result has 69 template identities. /examples [PAGE] [SEED] displays 24 cases per page in a deterministic round-robin over the six heuristic oracle levels and the core capability groups. Every entry shows the actual input, template, contract level, domain or capability, complexity where applicable, target strategy family, and metamorphic control. Page 1 therefore exposes the distribution instead of an accidental adjacent slice. The display permutation retains every case exactly once; the page header names its range and reproducible next-page command.

/smoke [COUNT] [SEED] executes cases from that catalog through a fresh offline regression runtime containing the generic core and QUICK fixture package, with the balanced work policy, default exact strategy set, Language Agent assistance disabled, and ordinary inability grounding disabled. It does not inherit session facts or interactive KB, memory, work, strategy, or normalization settings. Heuristic cases call the complete local wrapper and the same typed assessor as the generated-development runner. Established direct, preference, and typed-task cases call their ordinary public engine boundaries. A full run prints at least one actual input, expected contract, result, and pass state for every template plus every failure. All other cases remain in the total, and the summary groups execution by contract level, observed language route, and observed status.

The two commands serve different review needs. /examples exposes breadth and lets a programmer choose a representative input for manual investigation. /smoke is regression execution and protects already implemented behavior after changes. Neither command substitutes for a public benchmark: generated cases are project-owned software tests whose templates were inspired by capability families, not external benchmark rows.

The separately reported 1,200-case heuristic development suite

npm run benchmark:generated uses the shared heuristic generator and typed assessor under its own frozen seed, behavior identity, aggregates, failure clusters, and published receipt. /smoke intentionally instantiates the same 43 reviewed shapes under its smoke seed so an ordinary regression run cannot ignore near-CNL and complex language, then adds the 2,896 broader core cases. The generated report remains the strategy-research artifact. Its default receipt contains 1,200 unique surface inputs and observes 593 of 774 possible declared technique-by-domain cells. That is useful combination breadth, not 1,200 independent constructions or an independent domain-by-predicate design.

The report keeps every case in a fixed denominator and aggregates by structural domain, technique, target family, complexity, route, status, confidence, and resource outcome. Earliest-failure clusters combine the failed stage with the target family and preserve their technique and domain distributions. A maximum of 24 representative failures makes manual inspection manageable without hiding the size of a cluster. Repeated clusters justify a generic strategy hypothesis; a single memorable sentence does not. The same seed supports checkpoint comparison, while another seed tests the conclusion against new names and combinations.

Six oracle levels deliberately test different layers: answer execution, candidate selection, query-local decomposition, request execution, proposal-only preservation, and safety abstention. Candidate selection checks that the intended structural candidate wins, carries its required family, has a matching accepted parse-only reparse, and executes as the query-local interpreted episode under the declared route and status. It does not establish a complete relation-shaped query and may end UNKNOWN with missingEntity. A complex-clause proposal can satisfy its family and protected-operator checks while the final result remains UNPARSED; that row measures proposal reach and safety, not executable language coverage. The report shows each oracle level separately, while the top-level passed/total field remains a mixed contract rate that must be read together with route and status distributions.

This suite is deterministic internal development evidence with benchmarkComparable: false. Its HTML report and machine receipt remain separate from the five authored benchmark cases, the combined smoke result, and the public portfolio even though smoke deliberately reuses its generator shapes and oracle.

Acceptance discipline

A benchmark-guided fix must add a motivating positive case, at least one renamed or nonce case, a meaning-changing contrast, and a case that must remain unknown or unsupported when applicable. The test must assert semantic results and the relevant reasoning trace. A change fails review if the template generator contains the source record identifier, expected answer string, fixed person or relation copied from the evaluation item, or a branch on benchmark identity.
